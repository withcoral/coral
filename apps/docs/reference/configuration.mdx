Your configuration lives in the `config.toml` file of Coral's configuration folder. Where that folder is depends on how you run Coral:

- **Container image.** The `ghcr.io/withcoral/coral` image uses `/var/lib/coral/config`. Mount a volume at `/var/lib/coral` so the folder outlives the container. You can also pass the contents of `config.toml` in the `CORAL_CONFIG` variable. See [Container image](#container-image).
- **Coral Desktop.** Desktop uses the `runtime` folder of its data folder, for example `~/Library/Application Support/com.withcoral.app/runtime` on macOS. Desktop writes this `config.toml` again at each launch, so your edits to it are lost.
- **The `coral` binary.** When you start the binary yourself, it uses:
  - macOS: `~/Library/Application Support/com.withcoral.coral`
  - Linux: `~/.config/coral`
  - Windows: `%APPDATA%\withcoral\coral\config`

To use another folder with the container image or the binary, set `CORAL_CONFIG_DIR`.

Coral does not start when `config.toml` holds an unknown key, or a value that a key does not accept. The error names the key.

### `[outbound]`

Controls how Coral calls providers.

#### Network policies

`loopback` and `private_networks` set the policy for provider calls to those addresses.
Policies can have one of the following values:

- `deny`: Denies all requests to the policy target
- `https`: Allows only https requests, no plain http.
- `http-and-https`: Allows both http and https requests.

All provider calls not covered by an explicit policy in this section are treated under the `https` policy.

| Key                | Description                                                   | Required | Default                                  |
| ------------------ | ------------------------------------------------------------- | -------- | ---------------------------------------- |
| `loopback`         | Policy for provider calls to loopback addresses.              | No       | `deny`, or `http-and-https` without auth |
| `private_networks` | Policy for provider calls to addresses in non-public networks | No       | `deny`, or `http-and-https` without auth |

Without an `[auth]` section, `loopback` and `private_networks` default to `http-and-https`, so providers on your own machine and network work. With `[auth]`, both default to `deny`.

Coral ignores `HTTP_PROXY`, `HTTPS_PROXY` and `ALL_PROXY` for provider calls. It connects to each provider directly.

#### MCP OAuth clients

| Key                          | Description                                                                                           | Required | Default     |
| ---------------------------- | ----------------------------------------------------------------------------------------------------- | -------- | ----------- |
| `mcp_oauth_client_bootstrap` | How Coral identifies itself to an MCP provider's authorization server when nobody enters a client ID. | No       | `automatic` |

An MCP provider's authorization server can identify Coral in two ways. It can fetch Coral's Client ID Metadata Document from a URL, or Coral can register with Dynamic Client Registration. `mcp_oauth_client_bootstrap` selects between them:

- `automatic`: Coral uses the metadata document when the server supports it and the document's URL resolves to public addresses. Otherwise, Coral registers.
- `prefer-client-id-metadata-document`: Coral uses the metadata document whenever the server supports it. Use this with split DNS, or when the server can reach your internal network.
- `dynamic-client-registration-only`: Coral only registers. A failed registration does not fall back to the metadata document. If the server has no registration endpoint, enter a client ID for the provider.

The setting applies when Coral sets up a new OAuth client. It does not change a client ID that someone entered or a registration that Coral already holds.

### `[[secret_stores]]`

Defines a connection to a secrets system you run. Add one `[[secret_stores]]` table per store. Organization owners can see each store's name, kind and status in the account menu, under **Secret stores**. There they grant a store to a workspace, or revoke that grant. An archived workspace keeps its grants, and you cannot change them until you restore it. A grant whose store you remove from this file shows as **Removed from config**.

Each store has a `kind`: the secrets system it connects to. The other keys in its table depend on the kind.

| Key    | Description                                                                                                | Required | Default |
| ------ | ---------------------------------------------------------------------------------------------------------- | -------- | ------- |
| `name` | Stable name for the store: up to 64 lowercase letters, digits, `-` or `_`, starting with a letter or digit | Yes      | N/A     |
| `kind` | The secrets system, such as `env`. The other keys depend on the kind.                                      | Yes      | N/A     |

A store's name stands for one trust boundary. To point at a different store, add a new store under a new name.

Coral reads this section when it starts, and stores no credential for a store in its database.

- A malformed store stops Coral from starting. The error names the store and the field.
- An unreachable store does not stop Coral from starting.
- A store whose kind your build of Coral cannot read does not stop Coral from starting. Coral logs a warning, shows the store as **Not in this build**, and every read from it fails. Its grants and references stay.

A workspace owner uses a granted store when they connect a shared account: for each field, they choose **Use a secret store**, pick the store, and enter what its kind asks for. Coral reads the value once to check it, then reads it again for each call and keeps no copy.

#### Read from environment variables

The `env` kind reads each value from an environment variable of the Coral process. Use it when your platform injects secrets into the environment, for example from Kubernetes Secrets. Every build of Coral has it, on the Community Edition too.

```toml
[[secret_stores]]
name = "env"
kind = "env"
prefix = "MYCO_"
```

| Key      | Description                                                                         | Required | Default |
| -------- | ----------------------------------------------------------------------------------- | -------- | ------- |
| `prefix` | The start of every variable name the store can read: letters, digits and `_` only | Yes      | N/A     |

A workspace owner who chooses an `env` store enters one **Variable name**, such as `MYCO_API_KEY`. The form shows the prefix the name must start with. Coral reads only a name that starts with the prefix and holds letters, digits and `_` only, so a reference can never name a variable outside the prefix. Coral reads the variable each time it needs the value. A variable that is not set fails as an entry the store does not have, so Coral refuses to save a reference to it.

A grant of an `env` store to a workspace covers every variable under its prefix. So pick a prefix that holds only the secrets you mean to share. Coral refuses to start, and names the setting, when a prefix:

- is empty, or is the start of `CORAL_`, such as `C` or `CORAL`,
- starts with `CORAL_`, because those variables are Coral's own,
- covers a variable that another setting names, such as `credentials.key_env`, `database.url_env` or `listeners.run_executor.token_env`. Coral checks every setting whose name ends in `_env`.

Coral compares names without regard to case.

#### Limit what each store can read

The store's own policy is the security boundary, and Coral adds no check of its own. **A grant of a store to a workspace covers everything that store's role can read.** So give each store its own read-only role, with the least access that works, and use separate stores for workspaces that must not see each other's secrets.

### `[otel]`

Controls telemetry export to an OpenTelemetry endpoint.

Every request has a trace, even when you do not set `endpoint`. A failed MCP tool call returns its `trace_id`. `trace_filter` controls which spans Coral exports, not which requests are traced. Request spans use the target `coral.request`.

`trace_sample_ratio` controls which traces Coral exports. It applies to each trace Coral starts: a request without a valid caller `traceparent`, and each Program Run, which starts its own trace. A request with a valid caller `traceparent` follows the caller's sampled flag. An unsampled trace keeps its trace ID, so logs and tool failures still name it. Metrics are never sampled.

| Key            | Description                                                                        | Required | Default                                                                                                                                 |
| -------------- | ---------------------------------------------------------------------------------- | -------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| `endpoint`     | Base URL of an OTLP over HTTP endpoint. Coral sends to `/v1/traces`, `/v1/logs` and `/v1/metrics` under it. | No       | N/A                                                                                                                                     |
| `headers`      | Additional headers sent to the otel endpoint, formatted as `name=value,name=value` | No       | None                                                                                                                                    |
| `log_filter`   | Filters to apply to logs before otel export                                        | No       | `coral_app=info,coral_grpc=info,coral_mcp=info,coral_search=info,coral_administration=info,coral_provider::account::secret_references=info`                                             |
| `trace_filter` | Filters to apply to traces before otel export                                      | No       | `coral.request=trace,coral_app=trace,coral_grpc=trace,coral_mcp=trace,coral_run=trace,coral_search=trace,coral_search::index::reconcile=info,coral_upstream=trace,coral_administration=trace,coral.http.body=off,coral.mcp.body=off` |
| `service_name` | Name of the service when exporting OTEL data                                       | No       | `coral`                                                                                                                                 |
| `trace_sample_ratio` | Share of the traces Coral starts that it exports, from `0.0` to `1.0`        | No       | `1.0`                                                                                                                                   |

If `log_filter` or `trace_filter` is not a valid filter, Coral logs a warning and uses the default.

#### Trace UI requests

The UI reads the standard OpenTelemetry environment variables at startup, not `config.toml`. Set them on the UI process. The UI then opens one server span for each page, data and resource request. Each Coral gRPC call the request makes joins that trace. Send the UI and Coral to the same backend to see one trace for each UI request.

The UI also opens a span for each loader and action, and a client span for each Coral call. Coral's server span for a call is the child of its client span. UI spans carry the method, the route template, the status and the kind of a failure. They never carry headers, bodies, query strings, cookies or full URLs. A valid caller `traceparent` continues its trace, and an invalid one starts a new trace. The UI never reads or forwards `baggage` or `tracestate`. `/healthz` and `/readyz` open no span.

| Variable                                                              | Description                                                                                                                                        | Default                 |
| --------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------- |
| `OTEL_EXPORTER_OTLP_ENDPOINT`                                         | Base URL of an OTLP over HTTP endpoint. The UI sends traces to `/v1/traces` under it, as Coral does with `[otel].endpoint`. Use the same value for both. | None                    |
| `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT`                                  | Full URL for traces. The UI uses it as written, in place of `OTEL_EXPORTER_OTLP_ENDPOINT`.                                                           | None                    |
| `OTEL_EXPORTER_OTLP_PROTOCOL` or `OTEL_EXPORTER_OTLP_TRACES_PROTOCOL` | Must be `http/protobuf`. The UI does not start with any other value.                                                                                 | `http/protobuf`         |
| `OTEL_EXPORTER_OTLP_HEADERS`                                          | Additional headers, formatted as `name=value,name=value`                                                                                           | None                    |
| `OTEL_SERVICE_NAME`                                                   | Name of the service when exporting                                                                                                                 | `ui`                    |
| `OTEL_RESOURCE_ATTRIBUTES`                                            | Additional resource attributes, formatted as `name=value,name=value`                                                                               | None                    |
| `OTEL_TRACES_SAMPLER`                                                 | `always_on`, `always_off`, `traceidratio`, `parentbased_always_on`, `parentbased_always_off` or `parentbased_traceidratio`. The UI does not start with any other value. | `parentbased_always_on` |
| `OTEL_TRACES_SAMPLER_ARG`                                             | The ratio for the `traceidratio` samplers, from `0` to `1`                                                                                         | `1`                     |
| `OTEL_SDK_DISABLED`                                                   | Set to `true` to stop export                                                                                                                       | `false`                 |
| `OTEL_TRACES_EXPORTER`                                                | Set to `none` to stop export. The UI exports over OTLP with any other value.                                                                      | `otlp`                  |

The UI exports only when you set one of the two endpoint variables. The UI does not start if that value is not an `http` or `https` URL.

Coral follows the sampled flag on each UI call, so `OTEL_TRACES_SAMPLER` decides which of these traces Coral exports. When the UI does not export, it forwards only a valid caller `traceparent`, and Coral follows that caller's sampled flag. A gRPC call with no `traceparent` starts its own trace, and `trace_sample_ratio` decides if Coral keeps it.

The UI checks the endpoint, protocol and sampler values only when export is on.

#### Metrics

With `endpoint` set, you receive the `coral.*` metrics below. Their names, units and attributes are stable within a major version. No attribute holds an identifier, a provider name, a tool call path, a client or an endpoint. Durations are in seconds and sizes in bytes. Gauges show the value when Coral collects metrics, every 5 seconds.

- On `coral.request.duration`, `operation` is the route template or the gRPC method. An MCP tool call is `tools/call` followed by the tool's name, such as `tools/call exec`.
- On `coral.run.claims`, `operation` is the claim: `accept`, `start`, `recover` or `takeover`.
- `coral.run.queue.depth` counts the program runs on this Coral instance that are accepted but not started yet. A run starts right after it is accepted, so this is usually 0. A run that waits for recovery by another Coral instance is not counted.
- `coral.program.execution.heap.peak` is sampled each time a program waits and when it ends. A program that frees memory before it waits or ends shows less than its true peak.

No metric names a Secret Store. To find the store behind a slow or failing read, use the log records: each read logs `coral.secret_store.name`, `coral.secret_store.kind` and `coral.secret_store.read_ms`. A failed read logs at `warn` and adds `error.type`.

At most 2048 spans and 2048 log records wait for export. When a queue is full, the next span or log record is dropped and counted in `coral.telemetry.dropped` with `drop.reason` `queue_full`. A failed export counts its spans and log records with `export_failed`. Neither delays a request or a program run. Metrics are cumulative by default, so a failed export loses no metric points: the next export carries their totals. If you select delta temporality, the metric points of a failed export are counted too. If you see drops, check that your collector is reachable and keeps up.

#### Concurrency bottlenecks

Use these signals together to separate database admission, compiler saturation, search projection lag, and direct request CPU.

| Metric                                         | Kind      | Attributes                                 |
| ---------------------------------------------- | --------- | ------------------------------------------ |
| `coral.persistence.acquisition.duration`       | Histogram | `db.system`, `operation`, `outcome`        |
| `coral.persistence.acquisition.waiters`        | Gauge     | `db.system`, `operation`                   |
| `coral.compiler.request.duration`              | Histogram | `compiler.role`, `operation`, `outcome`    |
| `coral.compiler.queue.duration`                | Histogram | `compiler.role`, `operation`               |
| `coral.compiler.work.duration`                 | Histogram | `compiler.role`, `operation`, `outcome`    |
| `coral.compiler.isolate.build.duration`        | Histogram | `compiler.role`, `build.reason`, `outcome` |
| `coral.compiler.queue.depth`                   | Gauge     | `compiler.role`                            |
| `coral.compiler.active`                        | Gauge     | `compiler.role`                            |
| `coral.search.index.backlog`                   | Gauge     | `search.projection.kind`                   |
| `coral.search.index.backlog.sample.age`        | Gauge     | None                                       |
| `coral.search.index.first_visibility.age`      | Gauge     | None                                       |
| `coral.search.publication.visibility.duration` | Histogram | `outcome`                                  |
| `coral.search.index.recovery.duration`         | Histogram | None                                       |
| `coral.request.cpu.duration`                   | Histogram | `interface`, `operation`, `outcome`        |

**Database acquisition.** `operation` identifies `begin_write`, `begin_read_snapshot`, `execute`, `fetch_optional`, `fetch_all`, or `ping`. Acquisition duration covers the wait for a pooled connection. For transaction entry points, it also includes `BEGIN`. Direct-query execution is excluded. Outcomes are `ready`, `failed`, or `canceled`. A query failure after acquisition does not count as an acquisition failure. Transaction duration starts after acquisition. The waiter gauge counts callers awaiting acquisition; a detached Postgres `BEGIN` can finish after its caller cancels.

**Compiler.** `compiler.role` distinguishes the Run compiler (`run`) from the custom tool compiler (`authoring`). Each has one worker and 32 queue slots. Check depth, active work, waits, and outcomes by role. `operation` identifies `program`, `authored_tool`, or `analysis`. Request duration includes queueing and ends when the caller receives an answer. Outcomes distinguish `queue_full`, `stopped`, `timed_out`, `rejected`, `failed`, and `ok`. Queue depth includes enqueue attempts until they succeed or fail. An accepted job remains queued after its caller times out until the worker dequeues it. Work duration starts at dequeue and includes expiry checks. When a compile throws, is stopped, or exceeds its heap, the worker replaces its isolate before the next request. When the isolate grows too large, the worker replaces it too. Isolate build duration measures each replacement. `build.reason` is `fault`, `recycle`, or `retry`. `retry` means an earlier replacement failed, so a request built the isolate. A rising `fault` rate means compiles are throwing, reaching their deadline, or exceeding their heap. Read the request outcomes to tell these apart. `coral.program.compile.duration` still covers Program admission only. Its outcomes are `ok`, `rejected` for a Program Coral refused, `timed_out`, and `unavailable` for a busy, stopped, or failed compiler or a failed database read.

**Search backlog.** `search.projection.kind` distinguishes Provider catalog projections (`provider_catalog`), Private Tool projections (`private_tool`), and Shared Tool projections (`shared_tool`). These are units of indexing work, not counts of searchable Tools. Backlog includes missing or stale projections and failed retries that are not due yet. An observer runs in a separate supervised task, with shared shutdown, and takes read-only snapshots every 30 seconds. Each snapshot read has a 30-second limit. Failure logs identify the task and safe failure kind. A panicked task restarts after one second without stopping the other task. Check `sample.age` before trusting a count. A failed read reports no snapshot. A stopped observer removes its observation rather than reporting its last count.

**First visibility and recovery.** `first_visibility.age` covers only published Provider catalogs that have never been searchable. Renames and index-version rebuilds do not reset first visibility. The age is zero when none are waiting and absent when visibility history or the clock is unknown. Legacy failed projections can have unknown history; no first-visibility latency is invented for them.

`publication.visibility.duration` runs from the stored publication timestamp to the first successful index commit, including the publication transaction. `initial` identifies a first-attempt success; `retried` identifies success after failed initial attempts. Rewriting a complete projection records no visibility duration. If a previously searchable catalog becomes unavailable after a failed rebuild, `index.recovery.duration` measures from the first recorded failure to the recovery commit. Repeated failures preserve that start time. Visibility history survives restarts. Samples for replaced catalogs or failed visibility checks are omitted. Verification runs separately from index writes. The duration ends at the commit and excludes verification time. These signals exclude client setup time.

**Request CPU.** On Linux and macOS, CPU samples bracket each poll of the request handler and response body. Synchronous work in inline-awaited futures is included. Pending wait time, spawned tasks, and dedicated compiler or Program execution threads are excluded. The metric uses the same operation and outcome as request duration. Traces carry `coral.request.cpu_ns`, including when a handler is canceled. Sum CPU seconds by operation to attribute direct request work; this is not total process CPU. CPU histogram boundaries start at 10 microseconds and include sub-millisecond ranges. Other platforms omit the CPU signal.

#### Refresh tokens

Coral gives a refresh token with each access token to a client that lists `refresh_token` in its `grant_types`. This applies to registered clients and to clients with a Client ID Metadata Document. Other clients get access tokens only.

- **Lifetime.** Your users can refresh for `refresh_token_ttl_seconds` after they sign in. A refresh does not extend this time. When it ends, your users must sign in again.
- **Single use.** Each refresh returns a new refresh token, and the old one stops working. If a client sends a used token again, refresh stops for that sign-in, also for the newest token. Your clients must not refresh with the same token twice at the same time. If a refresh response is lost, the user may have to sign in again.
- **Current access.** Each refresh checks that the user is still an enabled member of the organization. For a workspace token, it also checks that the user is still a member of the workspace. A refresh does not contact your OIDC issuer. Changes you make at the issuer apply at the next sign-in. If you remove a membership, refresh stops for good, even if the user joins again.
- **Revocation.** To revoke a refresh token, send `token` and `client_id` to `<listeners.auth.public_url>/oauth/revoke`. A client registered with `client_secret_post` also sends its `client_secret`. Revocation stops refresh only. Access tokens that Coral already issued work until they expire. To cut off a user at once, disable or remove their organization membership: Coral then refuses their access tokens on the next request.
- **Storage.** Coral stores only a SHA-256 digest of each refresh token, in its database. Refresh tokens survive restarts. If you run more than one Coral process, give them the same database so that each process can refresh any token.

#### Web sessions

The web interface keeps your users signed in through a web session that Coral holds. At sign-in, the web interface gives its refresh token to Coral and keeps only a random session handle in a signed cookie. On each request, Coral mints a new access token for that session, which lasts at most five minutes. Your users stay signed in when an access token expires.

- **Lifetime.** A web session lasts `CORAL_WEB_SESSION_MAX_AGE_SECONDS` (default 2592000, 30 days) or until `refresh_token_ttl_seconds` ends, whichever comes first, and never longer than one year. Activity does not extend it. To keep users signed in longer, increase both values. To sign them out sooner, decrease the value that limits the session, or both.
- **Several processes.** Every web interface process reads sessions from Coral. You do not need shared storage for the web interface itself. Give every Coral process the same database and the same session signing key, and every web interface process the same `CORAL_WEB_SESSION_SECRET`, so that each process can finish a sign-in and serve a session that another one started.
- **Sign-out.** Signing out ends the session and its refresh token at Coral, and a copied session cookie stops working. Access tokens that Coral minted for the session before sign-out work until they expire, within five minutes.
- **Sign-out when Coral does not answer.** The browser still signs out. The next visit to the sign-in page finishes the sign-out at Coral. Until then, a copied session cookie still works, at most until the session would end.
- **Outages.** If Coral does not answer, the web interface shows an error and keeps the session. Your users stay signed in when Coral recovers.

## Usage data

Self-hosted Coral sends one anonymous usage report for each UTC day on which it runs. Sharing is on by default. Only official release builds send the data: Coral Desktop and the `ghcr.io/withcoral/coral` image.

Coral sends the report to `https://telemetry.withcoral.com/v1/report`. The [`[outbound]`](#outbound) policy still applies.

A report holds a random install ID, facts about your Coral build and where it runs, and dates, counts and totals of activity. It never holds your programs, tool arguments, tool results, credentials, names, email addresses or URLs. [`report.rs`](https://github.com/withcoral/coral/blob/main/crates/coral-usage/src/report.rs) lists every field. To read the exact report before Coral sends it, open **Help and feedback**, then **Usage data**.

Nothing in a report identifies you or your organization. We do not store IP addresses.

### Turn off sharing

If you are an organization owner, open **Usage data** and turn off **Share anonymous usage data**. This setting applies to the full deployment. Other members can read the page but cannot change it.

To stop sending from one Coral process, set one of these environment variables. Coral ignores spaces and letter case. Restart Coral after you change one. The **Usage data** page then shows a banner that names the variable.

| Variable                   | Stops sending when it is                        |
| -------------------------- | ----------------------------------------------- |
| `CORAL_DISABLE_USAGE_DATA` | Set to a value other than empty, `0` or `false` |
| `DO_NOT_TRACK`             | Set to a value other than empty, `0` or `false` |

When you turn off sharing, Coral stops sending. We keep the reports that Coral sent before.

## Container image

The `ghcr.io/withcoral/coral` image prepares `config.toml` before it starts Coral:

- **With `CORAL_CONFIG`.** The image writes the variable's value to `config.toml` at each start. Your edits to the file last until the next start. Coral does not start if a folder or a symbolic link is at that path.
- **Without `CORAL_CONFIG`.** The image keeps an existing `config.toml`. On a first start with an empty volume, it writes a starter file with user auth disabled. The starter binds gRPC to `127.0.0.1:14555`, MCP to `127.0.0.1:14556` and auth to `127.0.0.1:8779`, and sets the web UI to `http://127.0.0.1:3000`. To change a setting, edit the file and restart the container.

The image's Docker health check asks Coral's gRPC listener whether Coral is ready. It uses `127.0.0.1:14555` by default. If `[listeners.grpc]` binds another port, set `CORAL_HEALTHCHECK_ADDR` to a `host:port` that reaches it. Otherwise Docker never marks the container healthy. Kubernetes ignores this health check and uses the probes in your manifest.
