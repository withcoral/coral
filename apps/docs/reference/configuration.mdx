Coral stores local configuration in `config.toml` inside its platform-specific [local state directory](/getting-started/installation#local-state).

## Managed state

Coral writes source installation state to `config.toml` when you run commands such as `coral source add` and `coral source remove`.

This state includes installed-source metadata and non-secret source variables. Source secrets are stored separately within the same local trust boundary.

<Note>
  Prefer the `coral source` commands for source state instead of editing workspace entries manually.
</Note>

## Database

Coral stores durable app state in a local SQLite database named `coral.db` inside the local state directory by default. You do not need a `[database]` section for the default setup.

Use `[database]` to choose an explicit backend. Relative SQLite paths resolve from the local state directory.

```toml
[database]
backend = "sqlite"
path = "state/coral.db"
```

For Postgres, store the connection URL in an environment variable and reference the variable name from `config.toml`.

```toml
[database]
backend = "postgres"
url_env = "CORAL_DATABASE_URL"
```

```shellscript
export CORAL_DATABASE_URL="postgres://coral:secret@db.example.com:5432/coral?sslmode=verify-full"
```

<Note>
  Remote Postgres URLs must set `sslmode=verify-full` so Coral verifies the server identity. Loopback and local-socket Postgres URLs may omit TLS for local development.
</Note>

## Workspaces

A fresh Coral state has no workspaces. Create one explicitly before adding
sources:

```shellscript
coral workspace create work
```

Workspace names are ordinary names. In particular, `default` and names that
start with `default-` are neither created automatically nor reserved or
protected. Do not rely on any particular name as an implicit fallback in
scripts or deployment configuration.

Workspace records and membership live in Coral's configured database. Coral
keeps installed-source metadata and non-secret source variables in its local
state. Use `coral workspace` and `coral source` to manage that state instead of
editing workspace entries by hand. Source credentials remain scoped to the
workspace that owns their source installation.

There is no persisted active-workspace setting. For local CLI commands, Coral
selects a workspace in this order:

1. An explicit `--workspace <NAME>` flag.
2. A non-empty `CORAL_WORKSPACE` environment variable.
3. The sole local workspace, if exactly one exists.

When there are zero or multiple local workspaces and neither selector is set,
the command fails with guidance. It never chooses `default`, the first listed
workspace, or another fallback.

Workspace selection is separate from authorization. A local selector names the
workspace a CLI command requests; it does not grant access. For authenticated
MCP HTTP, the server is configured for one workspace and evaluates the caller's
membership for that workspace. A client cannot use an environment variable,
flag, or omitted selector to make the server route the request to another
workspace.

## Access mode and workspace membership

Without `[auth]`, Coral runs as a trusted single-user deployment. Its local
principal uses the `ImplicitOwner` policy: it can create and administer local
workspaces, and it is treated as an owner for local workspace access.

Adding `[auth]` switches the server to an authenticated shared deployment.
The local principal then uses the `NoLocalPrincipal` policy and is rejected;
being on the host does not grant access. A successful sign-in establishes an
identity only. It does not create a personal workspace, grant host-wide
superuser access, or make the signed-in person a member of any workspace.

Each shared workspace is access-controlled by its explicit membership:

| Role | Access |
| --- | --- |
| Owner | Read workspace data and manage the workspace, including its membership. |
| Member | Read workspace data only. |

Every newly created shared workspace is explicitly creator-owned. In shared
mode, a workspace with no non-local owner is omitted from membership listings
and workspace-scoped access and remains inaccessible. Coral emits a startup
warning that names those workspaces. Keep the warning: it identifies a state
that needs operator attention, not an alternate access path.

The gRPC API is Coral's internal contract boundary. It is not a supported
end-user workspace-administration or recovery surface.

Adding an existing member with the same role is idempotent; requesting a different role atomically moves the membership to that role. Coral refuses to demote or remove the sole owner.

### Repository recovery tool

The repository contains an off-by-default tool for recovering a legacy workspace with no non-local owner and for rebinding identities after an issuer rename. It is absent from shipped `coral` and default `xtask` builds. Use a checkout matching the deployment and back up first. Database possession is the authority: SQLite requires state-directory access; Postgres uses `[database].url_env` without a host-locality guarantee. The tool opens existing state without migrations or startup repair. Start the upgraded shared server, have the intended owner sign in once, then run:

```shellscript
cargo run -p xtask --features admin -- workspace-admin list-workspaces --state-dir /path/to/coral-state
cargo run -p xtask --features admin -- workspace-admin list-users --state-dir /path/to/coral-state
cargo run -p xtask --features admin -- workspace-admin set-owner --state-dir /path/to/coral-state --workspace work --user 00000000-0000-4000-8000-000000000000
```

`list-users` withholds provider subjects unless `--show-subjects` is explicit. `set-owner` adds or promotes an existing identity, preserves other memberships, refuses `coral:local`, and takes effect on the next request. State-directory precedence is `--state-dir`, then `CORAL_CONFIG_DIR`, then Coral's [local state directory](/getting-started/installation#local-state).

#### Rebinding a renamed issuer

For an issuer rename, verify stable subjects, stop Coral, back up, and note the expected affected-user count. Then run:

```shellscript
cargo run -p xtask --features admin -- workspace-admin rebind-issuer --state-dir /path/to/coral-state --from https://old.example --to https://new.example
```

Compare the count, update `[auth]`, restart, and test a login. Rebinding preserves internal IDs and memberships and excludes `coral:local`. Do not rebind when subjects changed, because the tool cannot prove identity continuity.

### Sign-in configuration

`[auth]` configures how Coral validates a sign-in; it is not a workspace access
list. The deployment owns the following configuration:

- `[auth.authorization_server]` names the issuer Coral exposes to its clients.
- `[auth.provider]` identifies the upstream OpenID Connect provider, client,
  callback, and provider-secret location.
- `[auth.session]` supplies the session-signing key from a file or environment
  variable.
- `[server.mcp_http]` identifies the public MCP resource when authenticated MCP
  HTTP is enabled.

The authorization-server issuer and the provider callback must describe the
same public origin. Store private key and provider-secret material outside
`config.toml`. Authentication config maps a successful sign-in to an identity;
membership remains the separate authorization decision described above.

Do not treat this configuration as a bootstrap shortcut. It does not seed a
workspace, assign an owner, or promote the machine running Coral. If shared
state has inaccessible workspaces, preserve the startup warning; do not invent
a gRPC or database-editing procedure as a user-access workaround.

## Server

The long-running `coral server` command reads its native gRPC bind address from
`[server]`:

```toml
[server]
bind_addr = "127.0.0.1:14555"
```

Without `[auth]`, the native gRPC listener does not authenticate clients. A
non-loopback bind exposes Coral and its configured sources to anyone who can
reach the port. Keep that listener on loopback or behind a trusted network
boundary.

With `[auth]`, gRPC is authenticated on Coral's private hop. It is still an
internal service boundary, not a public administration API. If that hop uses
cleartext HTTP/2 (h2c), bearer tokens remain exposed to the transport path;
use trusted loopback/private networking or terminate TLS before the h2c hop.

MCP Streamable HTTP is disabled by default. Enable its companion listener under
`[server.mcp_http]`:

```toml
[server.mcp_http]
enabled = true
bind = "127.0.0.1:14556"
```

Without `[auth]`, the MCP listener is restricted to loopback addresses. With
`[auth]`, configure the listener's public URL as the authenticated MCP resource
and place any non-loopback listener behind TLS. Do not send bearer tokens over
an untrusted cleartext h2c path.

## Runtime features

Experimental runtime features are configured under `[features]`.

```toml
[features]
feedback = true
```

You can inspect available features and their effective state with:

```shellscript
coral features list
```

Enable or disable a feature with:

```shellscript
coral features enable feedback
coral features disable feedback
```

Feature values must be booleans. Unknown feature keys are preserved in `config.toml` but ignored by Coral.

| Feature | Default | Description |
| ------- | ------- | ----------- |
| `database_sources` | `false` | Experimental. Enables installing and querying database sources. |
| `feedback` | `false` | Experimental. Exposes the MCP feedback tool when enabled. Feedback reports are stored locally and anonymous copies may be uploaded to Coral. |
| `observed_values_search` | `false` | Experimental. Collects, indexes, retrieves, and maintains values observed during earlier queries. |

## OpenTelemetry

External OpenTelemetry export is configured under `[otel]`.

```toml
[otel]
endpoint = "http://localhost:4318"
headers = "authorization=Bearer ..."
log_filter = "info"
trace_filter = "coral_app=debug"
service_name = "coral"
```

Trace history settings are configured under `[trace_history]`.

```toml
[trace_history]
enabled = true
retention_days = 7
```

See [Observe with OpenTelemetry](/guides/observe-with-opentelemetry) for the full telemetry setup guide.
