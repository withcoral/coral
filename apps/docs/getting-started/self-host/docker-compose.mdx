This guide will explain how to set up Coral using Docker Compose with your choice of SQLite or Postgres as the backing DB.

We will use `<coral-host>` as the placeholder for the domain of your Coral deployment.

## Before you start

- **Hostnames.** Coral serves the UI, its auth server and its MCP server on three public HTTPS URLs. This guide uses `<coral-host>`, `auth.<coral-host>` and `mcp.<coral-host>`. If you only have one hostname, see [Using a single hostname](#using-a-single-hostname).
- **OIDC client.** Create an OAuth/OIDC client at your identity provider and register this redirect URI:

  ```text
  https://auth.<coral-host>/auth/oidc/callback
  ```

  Coral derives the redirect URI from `listeners.auth.public_url`; there is no separate setting for it.

- **Images.** `latest` is the newest stable release. To pin a version, use a tag from the [releases page](https://github.com/withcoral/coral/releases) without the leading `v`, such as `ghcr.io/withcoral/coral:1.0.0`. The images are built for `linux/amd64` only. On an arm64 host, such as an Apple Silicon Mac, add `platform: linux/amd64` to both services to run them under emulation.

## Deploy

1. Create a compose file with the following contents on your working directory:

- See the [Configuration Reference](/reference/configuration) for more details on the configuration options.
- This compose file exposes no ports. Depending on how you intend to do TLS termination, either add the TLS termination container to this compose file (e.g. Caddy) or expose the ports 14556 (mcp), 8779 (auth) and 3000 (UI) to your reverse proxy so it can forward calls to Coral.
- Coral's gRPC should not be exposed outside the compose network. Be mindful the server is plaintext with no encryption.

<Tabs>
<Tab title="With SQLite">

```yaml
services:
  coral:
    image: ghcr.io/withcoral/coral:latest
    # Longer than the Shutdown Drain (30 s by default) plus the 6 s commit grace.
    stop_grace_period: 45s
    volumes:
      - coral-state:/var/lib/coral
    environment:
      CORAL_SESSION_SIGNING_KEY: ${CORAL_SESSION_SIGNING_KEY} # Used to sign JWT tokens
      CORAL_OIDC_CLIENT_SECRET: ${CORAL_OIDC_CLIENT_SECRET}
      CORAL_CONFIG: |
        [listeners.grpc]
        bind = "0.0.0.0:14555"

        [listeners.mcp]
        bind = "0.0.0.0:14556"
        public_url = "https://mcp.<coral-host>"

        [listeners.auth]
        bind = "0.0.0.0:8779"
        public_url = "https://auth.<coral-host>"

        [listeners.web]
        public_url = "https://<coral-host>"

        [auth.session]
        signing_key_env = "CORAL_SESSION_SIGNING_KEY"

        [auth.provider]
        issuer = "https://your-idp.example.com"
        client_id = "..."
        client_secret_env = "CORAL_OIDC_CLIENT_SECRET"
        bootstrap_owner_subject = "..."   # `sub` claim of the organization owner; see "Choosing the organization owner"
  coral-web:
    image: ghcr.io/withcoral/coral-web:latest
    depends_on:
      coral:
        condition: service_healthy
    environment:
      CORAL_ENDPOINT: http://coral:14555
      CORAL_WEB_ALLOW_INSECURE_CORAL_ENDPOINT: "1" # Plaintext connection to coral container
      CORAL_WEB_AUTH_MODE: required
      CORAL_WEB_PUBLIC_URL: https://<coral-host>
      CORAL_WEB_AUTH_ISSUER: https://auth.<coral-host>
      CORAL_WEB_SESSION_SECRET: ${CORAL_WEB_SESSION_SECRET} # to encrypt session cookies

volumes:
  coral-state:
```

<Note>
  Coral will save both the SQLite DB files and the encryption key for sensitive
  data in the `coral-state` volume.
</Note>

```yaml
services:
  coral:
    image: ghcr.io/withcoral/coral:latest
    # Longer than the Shutdown Drain (30 s by default) plus the 6 s commit grace.
    stop_grace_period: 45s
    environment:
      CORAL_DATABASE_URL: ${CORAL_DATABASE_URL}
      CORAL_CREDENTIALS_KEY: ${CORAL_CREDENTIALS_KEY}
      CORAL_SESSION_SIGNING_KEY: ${CORAL_SESSION_SIGNING_KEY}
      CORAL_OIDC_CLIENT_SECRET: ${CORAL_OIDC_CLIENT_SECRET}
      CORAL_CONFIG: |
        [listeners.grpc]
        bind = "0.0.0.0:14555"

        [listeners.mcp]
        bind = "0.0.0.0:14556"
        public_url = "https://mcp.<coral-host>"

        [listeners.auth]
        bind = "0.0.0.0:8779"
        public_url = "https://auth.<coral-host>"

        [listeners.web]
        public_url = "https://<coral-host>"

        [credentials]
        key_env = "CORAL_CREDENTIALS_KEY"

        [auth.session]
        signing_key_env = "CORAL_SESSION_SIGNING_KEY"

        [auth.provider]
        issuer = "https://your-idp.example.com"
        client_id = "..."
        client_secret_env = "CORAL_OIDC_CLIENT_SECRET"
        bootstrap_owner_subject = "..."   # `sub` claim of the organization owner; see "Choosing the organization owner"

        [database]
        backend = "postgres"
        url_env = "CORAL_DATABASE_URL"

  coral-web:
    image: ghcr.io/withcoral/coral-web:latest
    depends_on:
      coral:
        condition: service_healthy
    environment:
      CORAL_ENDPOINT: http://coral:14555
      CORAL_WEB_ALLOW_INSECURE_CORAL_ENDPOINT: "1"
      CORAL_WEB_AUTH_MODE: required
      CORAL_WEB_PUBLIC_URL: https://<coral-host>
      CORAL_WEB_AUTH_ISSUER: https://auth.<coral-host>
      CORAL_WEB_SESSION_SECRET: ${CORAL_WEB_SESSION_SECRET}
```

If your Postgres server uses a custom CA for TLS, add the CA bundle to the Coral container so Coral knows it can trust the certificate. For example, if you're using AWS RDS:

- Download the CA bundle:
  ```bash
  curl -sSo rds-ca.pem https://truststore.pki.rds.amazonaws.com/global/global-bundle.pem
  ```
- Mount it on the Coral container in the compose file:

  ```yaml
  coral:
    image: ghcr.io/withcoral/coral:latest
    volumes:
      - ./rds-ca.pem:/etc/coral/rds-ca.pem:ro
    environment: # unchanged
  ```

- Refer to the CA bundle in your `.env` file:
  ```dotenv
  CORAL_DATABASE_URL=postgres://coral:PASSWORD@<rds-endpoint>:5432/coral?sslmode=verify-full&sslrootcert=/etc/coral/rds-ca.pem
  ```

2. Create an .env file that will hold the credentials used by Coral

```dotenv
# Coral session signing key - create with:
# openssl ecparam -name prime256v1 -genkey -noout | openssl pkcs8 -topk8 -nocrypt -outform DER | base64 -w0
CORAL_SESSION_SIGNING_KEY=...

# Client secret from your OIDC provider's application settings.
CORAL_OIDC_CLIENT_SECRET=...

# Coral web session secret, at least 32 characters.
# openssl rand -hex 32
CORAL_WEB_SESSION_SECRET=...

# The following are only needed in the Postgres example

# Credential encryption key - create with: openssl rand -base64 32
CORAL_CREDENTIALS_KEY=...

# Postgres connection URL
CORAL_DATABASE_URL=postgres://coral:PASSWORD@db.example.com:5432/coral?sslmode=verify-full
```

3. Start Coral with `docker compose up -d`

   Both images have a built-in health check, which is what `condition: service_healthy` waits for. If `coral-web` reports `dependency coral failed to start`, the cause is in the `coral` container: run `docker compose logs coral`.

4. Start your reverse proxy for TLS termination. If you don't have one, you can use Caddy by merging it into the compose file:

```yaml
services:
  caddy:
    image: caddy:2
    ports:
      - "80:80"
      - "443:443"
      - "443:443/udp"
    volumes:
      - ./Caddyfile:/etc/caddy/Caddyfile:ro
      - caddy-data:/data
      - caddy-config:/config
    depends_on:
      coral:
        condition: service_healthy
      coral-web:
        condition: service_healthy

volumes:
  caddy-data:
  caddy-config:
```

Caddyfile:

```caddyfile
{
	email ops@example.com
}
<coral-host> {
	reverse_proxy coral-web:3000
}
auth.<coral-host> {
	reverse_proxy coral:8779
}
mcp.<coral-host> {
	reverse_proxy coral:14556
}
```

5. You should be able to open the UI in your browser in `https://<coral-host>`. After you create your first workspace you can use the UI instructions to connect an MCP client. Each workspace has its own MCP endpoint:

   ```text
   https://mcp.<coral-host>/workspaces/<workspace-id>/mcp
   ```

## Choosing the organization owner

`bootstrap_owner_subject` is the `sub` claim that your identity provider issues for the user who becomes the organization owner. It is not an email address. With Google it is a numeric account ID; other providers usually show it as the user ID in their admin console. You can also read it from the `sub` claim of an ID token issued to that user.

- Set it before that user signs in to Coral for the first time. Coral assigns the role at a user's first sign-in and does not change the role of a user who has already signed in.
- If you do not know the value yet, remove the line. An empty string is not valid and stops Coral from starting. Without an owner, organization admin operations are disabled.

## Using a single hostname

Each `public_url` is an origin: a scheme, a host and an optional port, with no path. Coral cannot be served under a path prefix. If you only have one hostname, as with Tailscale Serve, give each listener its own HTTPS port:

| Setting                                              | Example value                |
| ---------------------------------------------------- | ---------------------------- |
| `listeners.web.public_url`, `CORAL_WEB_PUBLIC_URL`   | `https://<coral-host>`       |
| `listeners.auth.public_url`, `CORAL_WEB_AUTH_ISSUER` | `https://<coral-host>:8443`  |
| `listeners.mcp.public_url`                           | `https://<coral-host>:10000` |

The redirect URI to register is then `https://<coral-host>:8443/auth/oidc/callback`.

## Troubleshooting

- **`coral-web` cannot reach the auth server.** `coral-web` calls the auth server at `CORAL_WEB_AUTH_ISSUER`, its public URL, from inside the compose network. That hostname must resolve and route from the containers, not only from your browser.
- **`/.well-known/openid-configuration` returns 404 on the auth server.** This is expected. Coral's auth server is an OAuth authorization server for the UI and MCP clients, not an OpenID provider. Its metadata is at `/.well-known/oauth-authorization-server`.
