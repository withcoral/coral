Coral can be run as a shared self-hosted server, allowing you and your team to share workspaces, provider and tool policies. You can also choose to share provider credentials with your team members on a given workspace if this is part of your workflow.

Self-hosted Coral has two major components:

- `coral`: Docker image with the Coral server. This includes the runtime, provider configuration, policies, authentication server and MCP server.
- `coral-web`: The UI you and your team can use to execute Coral management actions.

In this guide, we will walk you through setting up Coral with either Docker Compose or Kubernetes.

## Before you start

1. Make sure you have an OIDC compatible identity provider: Self-hosted Coral requires that you have your own IdP that Coral can use to authenticate users. Any OIDC compatible IdP will work, so if you use Okta, Google Workspace or WorkOS you're already good to go. You will need to configure an application on your IdP for Coral.
2. Choose your backing DB: Coral supports both SQLite and Postgres, with SQLite as the default. Choose what's appropriate for your setup. Postgres needs the pgvector extension for [search by meaning](/getting-started/self-host#search-by-meaning).
3. TLS termination: Coral requires the usage of TLS for user-facing connections, but Coral itself does not provide TLS support. You can use your preferred reverse proxy (e.g. nginx, envoy) or use Caddy if you don't have any.
4. Public endpoints: Coral uses three endpoints that must be visible to the user's system. We will use `<coral-host>` as the placeholder for the root domain of your Coral deployment:

- `<coral-host>`: URL for the `coral-web` UI.
- `auth.<coral-host>`: Auth endpoint, used by both `coral-web` and the MCP server to authenticate users.
- `mcp.<coral-host>`: MCP server endpoint.

Make sure you can configure the names to point to your Coral deployment (details in the deployment guides) and that you can create valid TLS certificates for these domains.

## Search by meaning

Your agents find tools by meaning as well as by words. A model in the Coral process compares the meaning of a query with the text of each tool. No text goes out of your deployment.

Search by meaning is on by default. To turn it off, set `semantic_search_enabled = false` in `[search]`. Restart Coral after you change the setting. See the [configuration reference](/reference/configuration#search).

### Postgres needs pgvector

With Postgres, search by meaning needs the pgvector extension, version 0.7 or later. With SQLite, you do not need to do anything.

Before you upgrade Coral on Postgres, install pgvector or turn the setting off.

At startup, Coral creates the `vector` extension when pgvector is installed and Coral's database role is a superuser. If the extension is not available, Coral does not start and reports an error such as:

```text
Error: failed precondition: Postgres 17.11 does not provide required search feature: vector extension (error returned from database: extension "vector" is not available); install pgvector 0.7 or later in a schema on Coral's search path, let Coral's database role create it, or set `[search] semantic_search_enabled = false`
```

To correct the error, do one of these steps:

- Install pgvector 0.7 or later on your Postgres server. Then, as a superuser, run `CREATE EXTENSION vector;` in Coral's database. Use a schema on the search path of Coral's database role.
- Set `semantic_search_enabled = false` in `[search]`. Coral then does not check for pgvector.

Many managed Postgres services include pgvector, for example Amazon RDS. On Amazon RDS, the master user can create the extension.

### The model

The `ghcr.io/withcoral/coral` image holds the model, so Coral does not download it.

Without the image, Coral looks for `model.onnx` and `tokenizer.json` in these folders, in this order:

1. `/opt/coral/models/bge-small-en-v1.5/`. Coral looks here on Linux only.
2. `models/bge-small-en-v1.5/` in Coral's [configuration folder](/reference/configuration).

If neither folder holds the files, Coral downloads them from GitHub. Until the files are ready, search matches by words only.

A host without network access cannot download the files. On such a host, do one of these steps:

- Download `model.onnx` and `tokenizer.json` from the [model release](https://github.com/withcoral/coral-releases/releases/tag/model-bge-small-en-v1.5-5c38ec7). Put both files in one of the folders above.
- Set `semantic_search_enabled = false` in `[search]`.

Coral uses a folder only when the SHA-256 of both files is correct. When Coral finds the files, its log shows `Coral search model ready in <folder>`.

### Cost

- **Memory.** The Coral process uses up to about 360 MiB more memory while it embeds tools.
- **CPU.** Coral embeds tools on one background thread at low priority. All workspaces share this thread.
- **Time.** A new or changed provider matches by words only until Coral embeds its tools. A provider with about 20,000 tools takes about 12 minutes on one x86 vCPU. Ten such providers take about two hours.
- **Database.** In Postgres, the vectors of 20,000 tools use about 26 MB. Search is fast while the database server keeps them in memory.
- **Disk.** The model files use about 133 MB.

### Older CPUs

On an x86-64 CPU, search by meaning needs the x86-64-v3 features, such as AVX2. On an older CPU, Coral starts and search matches by words only.

To examine a Linux host with glibc 2.33 or later, run `/lib64/ld-linux-x86-64.so.2 --help`. The CPU has the features when the output shows `x86-64-v3 (supported, searched)`.

Rosetta, which runs `linux/amd64` containers on Apple Silicon Macs, does not have these features.

## Upgrade from Coral 0.x

Coral 1.0 is a ground-up rewrite. Your agents now write TypeScript programs that call your providers, where 0.x ran SQL queries over sources. You manage Coral in the Coral UI instead of with `coral` commands, and your agents connect to the MCP server over HTTP instead of stdio.

That makes 1.0 a breaking change. It starts from fresh state and doesn't convert what 0.x stored, so your 0.x setup stays as it is until you're ready to switch.

When the Coral 1.0 runtime starts on a configuration folder or a database that an earlier version wrote, it stops and reports an error such as:

```text
pre-v1 Coral state detected at '<configuration folder>'; move or remove it before starting this version of Coral
pre-v1 Coral database state detected; move or remove it, or configure a fresh database before starting this version of Coral
```

Coral never deletes, converts or archives old state. Don't start a Coral 1.0 container on a 0.x volume, because the container overwrites `config.toml` there.

To start Coral 1.0:

1. Stop the old Coral. Copy its configuration folder, or its volume, and keep the copy for as long as you need it.
2. Give Coral 1.0 fresh state. Set `CORAL_CONFIG_DIR` to an empty folder or, in containers, mount a new volume. With Postgres, point Coral at an empty database.
3. Write a new configuration from the [configuration reference](/reference/configuration), or follow one of the guides below. Coral 1.0 rejects a 0.x configuration file.
4. Start Coral, then add your providers and connect your accounts again.
5. Point your agents' MCP clients at the new MCP endpoint.

To go back, stop Coral 1.0 and start the old version on the copy you kept.
