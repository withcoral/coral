Coral ships with a built-in MCP server that presents Coral to agents as a compact capability interface. Agents discover generated exports with `search` and `describe`, then run work through Code Mode with `exec` and `wait`.

<Note>
Before setting up a client, make sure you have [connected at least one source](/getting-started/quickstart).

</Note>

## What MCP clients get

| Type | Name       | Description                                                   |
| ---- | ---------- | ------------------------------------------------------------- |
| Tool | `search`   | Search current workspace exports and generated capabilities   |
| Tool | `describe` | Describe a typed ref, capability id, or unambiguous alias     |
| Tool | `exec`     | Run Code Mode, waiting briefly for fast completion            |
| Tool | `wait`     | Wait for new Code Mode output, or terminate a running run     |
| Tool | `feedback` | Blocked-agent feedback tool                                  |

Clients see generated TypeScript refs, SQL refs, capability ids, source identity, effect-profile summaries, and diagnostics. The MCP tool list is intentionally stable: adding or removing sources changes `search` and `describe` results, not the MCP tools themselves.
Successful MCP tool calls return structured JSON in `structuredContent`; Coral does not duplicate successful JSON payloads as fenced markdown text.

Use `coral --runtime-exposure typescript mcp-stdio` to expose only TypeScript invocation bindings, or `coral --runtime-exposure sql mcp-stdio` to expose only SQL projection bindings. The default is `both`. TypeScript-only exposure hides SQL refs and `coral.sql.query(...)`; SQL-only exposure hides generated TypeScript methods while leaving discovery and SQL Code Mode available.

### `search`

Use `search` to find generated exports. Arguments are optional unless you want to narrow the result set:

- `query`: text, typed ref, capability id, generated tool path, TypeScript path, or SQL ref
- `source_key`, `display_name`: source filters. `source_key` is the human-facing source handle (e.g. `"slack"`, `"github"`) and is the selector to reach for. To browse one source's whole surface, pass `source_key` with an empty `query`.
- `kind`: `typescript`, `sql_table`, or `sql_function` when SQL exposure is enabled; TypeScript-only exposure narrows this to `typescript`
- `capability_kind`: `query`, `mutation`, or `action`
- `effect`: `read`, `write`, `delete`, or `unknown`
- `intent`: `read`, `write`, or `any` — an explicit ranking hint that overrides write-verb detection on the query. `read` keeps reads-first ordering even for write-verb queries, `write` and `any` order every capability by content score alone. It never filters results.
- `expand_top`: embed the top hit's compact describe entry as a top-level `top` key, exactly as `describe` would return it. Exact-reference matches embed `top` automatically.
- `limit`, `offset`: pagination

Unknown arguments are rejected rather than silently ignored, so a typo like `source` or `provider` errors instead of degrading to an unfiltered search.

Exact typed-ref, capability-id, generated tool path, TypeScript-path, and SQL-ref matches rank ahead of text matches. For text queries, read-vs-write is a hard ordering tier rather than a score nudge: unless the query contains a write-intent verb (`create`, `merge`, `close`, `assign`, `publish`, ...), capabilities with read effects rank before unknown-effect capabilities, which rank before mutations, no matter how strongly a mutation's parameter text matches; queries that do contain a write-intent verb rank all capabilities in one tier so reads stay reachable. An explicit `intent` argument overrides this verb detection in either direction. Within a tier, ranking is recall-first and provider-agnostic: any capability whose title, description, or **input-parameter names and descriptions** overlap the query is returned (it is never gated away before ranking), with common terms down-weighted by inverse document frequency. Search results are structured for agents: each item includes a preferred `ref`, generated Code Mode `call` path when TypeScript is visible, a one-line call `signature` (required parameters first, optional as `name?: type`, enums abbreviated, capped with `…+N`, plus a `-> value:` return hint) for that call path, SQL `sql` ref when SQL is visible, `source_key`, `capability_kind`, `effect` or `effects`, `title`, `description`, a page-relative `score`, an absolute `raw_score` for cross-page comparison, `matched_terms`, `matched_fields`, `rank_reason`, and `input_schema_available`. Default values such as `support: "generated"`, `deprecated: false`, and zero diagnostics are omitted. When the top hit is an exact-reference match (or `expand_top: true` is passed), the response also carries `top`: the top hit's compact describe entry, identical to a `describe` call, so exact-ref lookups need no second round trip. Top-level `pagination` reports `limit`, `offset`, `total`, and `next_offset`; top-level `diagnostics` reports workspace discovery problems, such as installed sources whose generated artifacts need to be regenerated.

### `describe`

Use `describe` before invoking anything. Pass `reference` as a generated tool path such as `tools.github.rest.issues.list`, a typed ref such as `typescript:github.rest.issues.list`, a SQL ref such as `sql_table:github_rest.issues` or `sql_function:github_rest.search`, a capability id, or an unambiguous alias.

If an untyped reference is ambiguous, `describe` returns grouped candidates instead of guessing. Retry with a typed ref from the candidate list. If a source is installed but stale, not-found responses include top-level `diagnostics` instead of silently looking like the source does not exist.

For found capabilities, MCP `describe` defaults to a compact invocation contract: preferred `ref`, generated `call` path when TypeScript is visible, SQL `sql` ref when SQL is visible, `source_key`, `capability_kind`, `effect` or `effects`, title/description, `input_schema`, `value_schema` (the provider value shape, without the generated result envelope), structured examples, SQL bindings, and diagnostics. It does not encode argument schemas as prose strings. Input schemas reference shared named provider types (for example recursive GraphQL filter inputs) through a root `$defs` block with `#/$defs/<TypeName>` `$ref`s, so each named type is defined once instead of being re-inlined at every argument.

Compact schemas are size-bounded: oversized rendered subtrees are replaced with `{ "type": ..., "x-coral-truncated": true }` stubs, the entry carries `input_schema_truncated`/`value_schema_truncated` flags plus a `schema_note`, and `$defs` entries that become unreachable are dropped. When depth pruning alone cannot meet the renderer budget (flat named-type graphs such as recursive GraphQL filter inputs), whole `$defs` entries are kept in body-reachability order until the budget fills and `$ref`s to the dropped far types become truncation stubs, so near types stay fully described. To expand one renderer-elided subtree, pass `path` as a dot path into the input schema (for example `path: "filter"` or `path: "filter.team"`); prefix `output.` to address the value schema. Path responses are `{ ref, call, path, schema, elided }`, where `elided` lists subtrees that were re-elided by bounding. Pass `schemas: "full"` to skip renderer-size bounding; this cannot recover source/importer-level `x-coral-truncated` stubs already present in the materialized source artifact. Use `describe` with `view: "detailed"` when you need full provider artifacts, credential requirements, or generated export provenance. Successful generated calls resolve directly to the provider value described by `value_schema`.

Code Mode's `coral.describe` returns the identical compact entry (wrapped in `{ status, found, ambiguous, entry, diagnostics }`) and accepts the same `path` and `schemas` keys.

### `exec` and `wait`

Use Code Mode for execution. `exec` accepts JavaScript source in the `source` argument and returns `{ run, result, output, cursor }`. `run.status` is the execution status. `result` is the script's return value directly and is omitted when the script returns nothing. `output` is the run's console text joined into one string, omitted when empty. Non-text content items (for example images) arrive in an `events` array, also omitted when empty. While `run.status` is `"running"`, the response carries a `cursor`; pass it back as `wait { run_id, cursor }` to receive only newer output — the cursor advances by underlying event id, so resumed waits never re-deliver or skip output. Failures add `error: { cause, message }`, and in-flight or failed nested calls appear as `tool_calls`. To stop a running run, call `wait` with `terminate: true`. An optional first-line pragma `// @exec: {"yield_time_ms": 10000, "max_output_tokens": 10000}` tunes how long `exec` waits for completion before returning a running run and the result-size budget.

Code Mode runs in Coral's V8 isolate. Supported globals are generated `tools.*`, Coral helpers under `coral.*`, standard JavaScript, `console.*`, and the documented helpers in the `exec` description.

Code Mode exposes Coral host helpers and generated provider methods:

```javascript
await coral.search({ query: "github issues" });
await coral.describe({ reference: "tools.github.rest.issues.list" });
await coral.describe({ reference: "tools.github.rest.issues.list", path: "filter.team" });
await coral.sql.query("select * from github_rest.issues limit 5");
// Successful generated calls resolve directly to the provider value.
const issues = await tools.github.rest.issues.list({ owner: "withcoral", repo: "coral" });
// Optional second argument: collect slim diagnostics instead of throwing,
// or request the transport envelope.
const result = await tools.github.rest.issues.list(
  { owner: "withcoral", repo: "coral" },
  { allowErrorResult: true, envelope: true }
);
if (!result.ok) return result.error;
return { issues: result.value, status: result.envelope.provider.status };
```

When TypeScript exposure is disabled, generated TypeScript methods fail before capability invocation. When SQL exposure is disabled, `coral.sql.query(...)` and SQL refs are hidden.

Generated TypeScript methods call `CapabilityService.Invoke` inside Coral. They do not call providers directly, do not receive credentials, and do not bypass source-level provider auth. Query, mutation, and action capabilities are callable by default. For dynamic workflows, use `call` from `search` or `describe` and call the generated method under `tools.*` inside Code Mode. Generated methods reject on provider or transport failure by default; the rejection is catchable with JavaScript `try`/`catch`, and an uncaught rejection fails the run. A successful call resolves directly to the provider value — if it resolves, it is the provider value. MCP capabilities resolve `structuredContent`; when an upstream MCP server returns no `structuredContent` but does return one text block containing exact JSON or one `json` fenced code block, Coral parses that JSON into the resolved value. Two per-call options change the resolved shape. `{ allowErrorResult: true }` resolves slim `{ ok, value, partial, error: { kind, message, details } }` diagnostics instead of throwing on provider failure; `partial: true` marks incomplete provider data. `{ envelope: true }` resolves `{ ok, value, error, envelope }`, where `envelope.provider` carries transport metadata only — REST `status` and lowercase response headers at `envelope.provider.headers` (for Link-header pagination and rate-limit debugging), GraphQL `errors`/`extensions`, raw MCP `content` — and never duplicates the provider payload, which is only in `value`. Provider error details are bounded structured diagnostics when available, such as HTTP status/body previews, MCP protocol errors, or MCP `isError` tool results.

Code Mode enforces explicit default nested-call budgets. A run fails at the top level when it exceeds `max_nested_tool_calls=100` or `max_parallel_tool_calls=100`; total nested invocations are counted by `max_nested_tool_calls`. Budget errors include the limit name, configured value, observed count, and invocation path. Direct results default to `max_output_tokens=10000` unless overridden with the first-line `// @exec` pragma; an oversized direct result still completes the run, `result` becomes the truncated preview (parsed back to JSON when possible), and a sibling `result_truncated` reports `original_bytes`, `estimated_tokens`, and an `artifact: { path, bytes }` when Coral can spill the complete JSON result to disk. Spilled direct results are capped by `max_output_result_spill_bytes=1048576`; larger results still return the preview in `result` and `result_truncated` without an artifact. Verbose `console.*` diagnostics are bounded separately; when Coral truncates, drops, or spills console text, the response carries an `output_truncated` field with the limit name, observed/dropped counts, and `full_output_path` when available. Spilled console text is capped by `max_output_text_spill_bytes=1048576`; after that, diagnostics are dropped with metadata instead of failing the run or growing the spill file indefinitely.

When a SQL binding exists, run SQL from Code Mode through `coral.sql.query(...)`. Coral does not expose direct SQL MCP tools.

Coral uses stdio transport. If a client supports a command-based install flow, point it at `coral mcp-stdio`.

## Verify the connection

Once your client is connected, ask the agent to search available capabilities or run a small Code Mode SQL query. Examples:

> "Search Coral for GitHub issue capabilities."

> "Run `select 1` through Coral Code Mode."

The agent should call `search` to find generated call paths and typed refs, `describe` to inspect JSON schemas, and `exec` to run Code Mode. While `run.status` is `"running"`, the agent calls `wait` with the returned `cursor`. SQL runs inside Code Mode with `coral.sql.query(...)`.

## Troubleshooting

- **`coral` not found:** Make sure `coral` is on your `PATH`, or use the full path from `which coral` on macOS or Linux or `(Get-Command coral).Source` in PowerShell.
- **No tables visible:** Confirm SQL exposure is active, then run `search`/`describe` to see whether installed sources project `sql_table:*` or `sql_function:*` refs. Some sources expose generated TypeScript capabilities without SQL projections.
- **No capabilities visible for an installed source:** Inspect `diagnostics` from `search` or `describe`. `SOURCE_ARTIFACTS_UNAVAILABLE` means the source must be re-added so Coral can regenerate its capability artifacts.
