title: "Write a custom source spec"
description: "Extend Coral by adding an API, upstream MCP server, GraphQL endpoint, or local dataset."
---

Coral sources use `SourceSpec` YAML. A source spec declares provider interfaces;
Coral snapshots those interfaces, generates capabilities, then builds
TypeScript bindings, SQL bindings when the shape is suitable, and discovery
metadata.

You do not hand-author tables, columns, table functions, or provider callables.
Those are generated downstream from provider snapshots and capabilities.

<Tip>
  Install the [Coral source spec authoring
  skill](/getting-started/installation#skills) with `npx skills add
  withcoral/skills` to help your coding agent write SourceSpec files.
</Tip>

## Will This Work?

Custom sources work best when the provider has one of these entry points:

- an OpenAPI 3.0 document for a REST API
- an upstream MCP server with `tools/list`
- a GraphQL endpoint with SDL or introspection
- explicit local files in `json`, `jsonl`, `csv`, or `parquet` format

Declare credentials as source inputs. API keys, bearer tokens, OAuth access
tokens, passwords, private keys, and authorization header values must be
`kind: secret`, even when read-only. Coral stores values locally and resolves
them during materialization or invocation; generated artifacts contain
credential requirements, never secret values.

Provider, descriptor, schema, and OAuth credential endpoint URLs must use
HTTPS. HTTP is only accepted for localhost or loopback development fixtures;
OAuth endpoint templates are checked after source inputs are rendered.

## Authoring Workflow

1. Write a `spec_version: 1`, `kind: source` YAML file.
2. Run `coral source lint ./my-source.yaml`.
3. Add it with `coral source add --file ./my-source.yaml` or
   `coral source add --interactive --file ./my-source.yaml` when inputs should
   be prompted.
4. Run `coral source test <source_name>` if the spec declares `test_queries`.
5. Use Coral over MCP or the CLI to inspect generated exports:
   - MCP: `search`, then `describe`
   - CLI SQL: `coral sql "SELECT ..."` when SQL bindings exist
6. Refine the provider document or SourceSpec interface declarations and repeat.

## Example: Local JSONL Source

Create sample data:

```shellscript
mkdir -p demo-data
cat > demo-data/messages.jsonl <<'EOF'
{"type":"user","session_id":"s1","text":"hello"}
{"type":"assistant","session_id":"s1","text":"world"}
EOF
```

Create `local-messages.yaml`:

```yaml
spec_version: 1
kind: source
name: local_messages
description: Demo local messages
test_queries:
  - SELECT * FROM local_messages.messages LIMIT 1
interfaces:
  - id: messages
    type: file
    files:
      - /absolute/path/to/demo-data/messages.jsonl
    format:
      kind: jsonl
```

Replace `/absolute/path/to/demo-data/messages.jsonl` with the real absolute
path on your machine.

Add and validate:

```shellscript
coral source lint ./local-messages.yaml
coral source add --file ./local-messages.yaml
coral source test local_messages
```

If the file format and schema are suitable, Coral generates a file read
capability plus SQL bindings. Query the SQL projection with:

```shellscript
coral sql "
  SELECT type, session_id, text
  FROM local_messages.messages
  ORDER BY session_id, type
"
```

## Example: OpenAPI Source

Use an OpenAPI interface when the provider publishes an OpenAPI document:

```yaml
spec_version: 1
kind: source
name: demo_api
description: Demo REST API
inputs:
  - key: API_TOKEN
    kind: secret
    label: API token
interfaces:
  - id: rest
    type: openapi
    file: ./openapi.yaml
    base_url: https://api.example.com
    auth:
      kind: bearer_input
      key: API_TOKEN
```

Use `url:` instead of `file:` when the OpenAPI document is available over HTTPS:

```yaml
interfaces:
  - id: rest
    type: openapi
    url: https://api.example.com/openapi.json
    base_url: https://api.example.com
```

OpenAPI import preserves operation ids, parameters, request media types,
response variants, security requirements, and provenance. Coral turns supported
operations into capabilities. Read-like, row-shaped capabilities may also get
SQL bindings; mutations remain discoverable and callable through TypeScript
when the experimental mutation gate permits invocation.

OpenAPI `url` and `base_url` values may be literal URLs or HTTPS templates
using `{{input.KEY}}` tokens. Template tokens must reference declared
`kind: variable` inputs, not secrets, and must not include inline defaults.
Coral validates the rendered URL during source materialization and invocation.
When using local `file:` descriptors, `coral source add --file` resolves
relative paths from the manifest directory; direct API imports must send
absolute paths.

If the interface has `auth`, Coral uses it while fetching the OpenAPI `url`
only when that descriptor URL is same-origin with `base_url`. Public OpenAPI
documents hosted on a different documentation or source-control origin are
fetched without provider credentials.

## Example: Upstream MCP Source

Use an `mcp` interface when the provider exposes tools through an upstream MCP
server. This is not Coral's own MCP server surface; it is a provider interface
that Coral imports.

```yaml
spec_version: 1
kind: source
name: demo_tools
inputs:
  - key: API_TOKEN
    kind: secret
interfaces:
  - id: tools
    type: mcp
    server:
      transport:
        type: streamable_http
        url: https://mcp.example.com/mcp
      auth:
        kind: bearer_input
        key: API_TOKEN
```

For a trusted local stdio server:

```yaml
interfaces:
  - id: tools
    type: mcp
    server:
      transport:
        type: stdio
        command: github-mcp-server
        args: []
      env:
        - name: GITHUB_TOKEN
          key: API_TOKEN
```

Coral snapshots `tools/list`, maps MCP `ToolAnnotations` to effect profiles
using MCP defaults, and generates one capability per supported tool. It does not
infer effects from tool names or descriptions. Most MCP tools are TypeScript
callable only. SQL bindings are generated only for read tools with structured
output schemas.

Streamable HTTP `url` values may be literal URLs or HTTPS templates using
`{{input.KEY}}` tokens. Template tokens must reference declared variable inputs,
not secrets, and must not include inline defaults. Coral validates the rendered
endpoint during source materialization and invocation.

## Example: GraphQL Source

Use a `graphql` interface when the provider exposes a schema:

```yaml
spec_version: 1
kind: source
name: demo_graphql
inputs:
  - key: API_TOKEN
    kind: secret
interfaces:
  - id: graph
    type: graphql
    endpoint: https://api.example.com/graphql
    auth:
      kind: bearer_input
      key: API_TOKEN
    schema:
      kind: introspection_query
```

Schema can also come from SDL or introspection JSON:

```yaml
schema:
  kind: sdl_file
  file: ./schema.graphql
```

```yaml
schema:
  kind: introspection_json_url
  url: https://api.example.com/graphql-schema.json
```

GraphQL import extracts supported root `Query` and `Mutation` fields, including
fields with arguments and object/connection return types. Coral generates
bounded operation documents with GraphQL variables, shallow scalar selections,
and connection-style `nodes`/`pageInfo` selections when the schema exposes that
shape. `Query` fields default to read/idempotent; `Mutation` fields default to
write/non-idempotent. Subscriptions, authored operation refinements, custom
pagination profiles, and user-authored row shapes are not SourceSpec fields in
this branch.

Deprecated root GraphQL fields are recorded in the provider snapshot as
unsupported operations and are not exposed as generated capabilities. If Coral
reports stale or incompatible generated GraphQL artifacts after a binary
upgrade, re-add the source so operation documents and exports are regenerated
from the current schema.

GraphQL `endpoint` and live-introspection endpoint overrides may be literal URLs
or HTTPS templates using `{{input.KEY}}` tokens. Template tokens must reference
declared variable inputs, not secrets, and must not include inline defaults.
SDL and introspection JSON schema URLs remain literal descriptor URLs.

GraphQL SQL bindings are generated only when a query has a deterministic,
row-shaped output. Mutations and ambiguous output shapes remain TypeScript
callable only.

## Inputs And Auth

Top-level `inputs` are shared by all interfaces. An interface may also declare
its own `inputs`; keys are merged and must not conflict.

```yaml
inputs:
  - key: API_BASE
    kind: variable
    default: https://api.example.com
  - key: API_TOKEN
    kind: secret
    required: true
```

For interactive OAuth collection, put the OAuth contract on the secret input:

```yaml
inputs:
  - key: API_TOKEN
    kind: secret
    credential:
      methods:
        - type: oauth
          label: Connect with OAuth
          oauth:
            flow:
              type: authorization_code
              pkce: required
            redirect_uri: http://localhost:53682/oauth/callback
            redirect_uri_port_mode: fixed
            endpoints:
              authorization_url: https://provider.example.com/oauth/authorize
              token_url: https://provider.example.com/oauth/token
            client:
              id:
                input: PROVIDER_OAUTH_CLIENT_ID
            scopes:
              scope:
                delimiter: comma
                values:
                  - read:data
```

Use `client.id.default` when the source can ship a public client id. Add
`client.secret.input` only for providers that require confidential OAuth.

Supported auth descriptors are:

```yaml
auth:
  kind: bearer_input
  key: API_TOKEN
```

```yaml
auth:
  kind: header_input
  name: X-API-Key
  key: API_TOKEN
```

```yaml
auth:
  kind: headers
  headers:
    - name: X-API-Key
      key: API_TOKEN
    - name: X-Application-Key
      key: APPLICATION_KEY
```

```yaml
auth:
  kind: none
```

Auth keys must reference declared secret inputs. Secret values never enter
provider snapshots, capabilities, source exports, workspace exports, logs, MCP
results, or Code Mode globals.

During materialization, descriptor/schema acquisition does not blindly reuse
runtime auth. OpenAPI and GraphQL descriptor URLs receive interface auth only
when they are same-origin with the runtime `base_url` or GraphQL `endpoint`.

## Validation Queries

`test_queries` are optional read-only SQL checks. Use them when the source is
expected to produce SQL bindings:

```yaml
test_queries:
  - SELECT * FROM demo_api.messages LIMIT 1
```

Keep validation queries cheap and bounded. `coral source add --file` reports
post-install validation issues as warnings; `coral source test <source_name>`
is the strict rerun.

## Tips

- Start with one interface and add more once materialization works.
- Prefer provider documents over hand-written examples; Coral generates
  capabilities from provider snapshots.
- Use `search` and `describe` over MCP to inspect generated exports before
  invoking anything.
- Use typed refs such as `typescript:*`, `sql_table:*`, and `sql_function:*`
  when describing generated exports.
- Keep local file specs explicit. A file interface names trusted files; it is
  not a grant for arbitrary filesystem traversal.
