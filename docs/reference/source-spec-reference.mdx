---
title: "Source spec reference"
description: "Schema and fields for Coral SourceSpec YAML files."
---

Coral source specs declare provider interfaces. During `coral source add`,
Coral acquires raw interface inputs, builds provider snapshots, generates a
`SourceCapabilitySet`, and builds source exports. SQL tables/functions and
TypeScript bindings are generated outputs, not authored source-spec fields.

<Tip>
  For examples and workflow guidance, see [Write a custom
  source](/guides/write-a-custom-source).
</Tip>

## Top-Level Fields

Every SourceSpec starts with `spec_version: 1` and `kind: source`:

```yaml
spec_version: 1
kind: source
name: my_source
description: Optional display description
inputs: []
interfaces: []
test_queries: []
```

| Field | Required | Description |
| --- | --- | --- |
| `spec_version` | Yes | Must be `1`. |
| `kind` | Yes | Must be `source`. |
| `name` | Yes | Install-time proposal for the display name and initial source key. It is not stable identity. |
| `description` | No | Human-readable source description. |
| `inputs` | No | Source-level variable and secret declarations shared by interfaces. |
| `interfaces` | Yes | One or more provider interfaces. Supported types are `openapi`, `mcp`, `graphql`, and `file`. |
| `test_queries` | No | Optional read-only SQL checks for generated SQL bindings. |

Fields outside SourceSpec v1 are rejected.

During `coral source add`, pass `--interfaces <id[,id...]>` to install only a
subset of a multi-interface source. Coral filters the effective SourceSpec
before collecting inputs and materializing artifacts, so inputs used only by
unselected interfaces are not required and the installed source exposes only the
selected interfaces.

## Identity

`name` is not source identity. When a source is installed, `coral-app` assigns:

- immutable `source_id`
- immutable `source_key`
- mutable `display_name`

Generated capability ids, SQL refs, TypeScript refs, and installed artifacts
use app-assigned source identity. Renaming the display name does not rewrite
capability identity or binding paths.

## Source Inputs

Inputs declare values Coral collects and stores locally:

```yaml
inputs:
  - key: API_BASE
    kind: variable
    default: https://api.example.com
    allowed_values:
      - https://api.example.com
    label: API base URL
    required: true
  - key: API_TOKEN
    kind: secret
    label: API token
    required: true
```

| Field | Required | Description |
| --- | --- | --- |
| `key` | Yes | Input key referenced by auth/env descriptors. |
| `kind` | Yes | `variable` or `secret`. |
| `required` | No | Defaults to `true`. |
| `default` | No | Default value for variables. |
| `allowed_values` | No | Exact allowed values for variables. Empty or omitted means unconstrained. Defaults must be included when this is set. |
| `label` | No | Short prompt/display label. |
| `hint` | No | Longer prompt guidance. |
| `credential` | No | Credential retrieval methods for secret inputs. |

Declare credentials as `kind: secret`. This includes API keys, bearer tokens,
OAuth access tokens, passwords, private keys, and authorization header values.
Use `allowed_values` for non-secret variables that influence credentialed
provider hosts, regions, sites, or other constrained provider routing.

Interface-level `inputs` are allowed and are merged with top-level inputs. A
duplicate input key must have the same declaration everywhere it appears.

Secret inputs may declare credential retrieval methods. `source_config` uses
the normal env-var or prompt path. `oauth` lets `coral source add
--interactive` retrieve and store the secret through Coral's OAuth helper:

```yaml
inputs:
  - key: API_TOKEN
    kind: secret
    credential:
      methods:
        - type: oauth
          label: Connect with OAuth
          oauth:
            flow:
              type: authorization_code
              pkce: required
            redirect_uri: http://localhost:53682/oauth/callback
            redirect_uri_port_mode: fixed
            endpoints:
              authorization_url: https://provider.example.com/oauth/authorize
              token_url: https://provider.example.com/oauth/token
            client:
              id:
                default: provider-client-id
                input: PROVIDER_OAUTH_CLIENT_ID
            scopes:
              scope:
                delimiter: comma
                values:
                  - read:data
        - type: source_config
          label: Paste token
```

OAuth flow `type` may be `authorization_code` or `device_code`. PKCE is
`required` or `disabled`. Redirect port mode is `fixed` or `random`; fixed
redirects must include an explicit non-zero localhost or loopback port. OAuth
client secrets are optional and, when used, declare `client.secret.input` plus
`client.secret.transport` as `basic_auth` or `request_body`.

## Auth Descriptors

OpenAPI, MCP Streamable HTTP, and GraphQL interfaces may use these auth
descriptors:

```yaml
auth:
  kind: bearer_input
  key: API_TOKEN
```

```yaml
auth:
  kind: header_input
  name: X-API-Key
  key: API_TOKEN
```

```yaml
auth:
  kind: headers
  headers:
    - name: X-API-Key
      key: API_TOKEN
    - name: X-Application-Key
      key: APPLICATION_KEY
```

```yaml
auth:
  kind: none
```

Auth keys must reference declared secret inputs. `kind: headers` sends each
listed header from its referenced secret input. Auth describes where the
app-resolved value is placed on the wire. It does not store values in
materialized artifacts.
When Coral fetches OpenAPI or GraphQL descriptor/schema URLs during source
materialization, it reuses interface auth only when that acquisition URL is
same-origin with the runtime `base_url` or GraphQL `endpoint`. Cross-origin
public descriptors are fetched without provider credentials.

OpenAPI `url` and `base_url`, MCP Streamable HTTP
`server.transport.url`, GraphQL `endpoint`, and GraphQL live-introspection
endpoint overrides may be HTTPS templates using `{{input.KEY}}` tokens. URL
template tokens must reference declared `kind: variable` inputs, not secrets,
and must not include inline defaults. Coral validates the rendered URL during
materialization and invocation. HTTP remains limited to localhost or loopback
development URLs.
When a URL-template variable selects a credentialed provider host or site, the
input should declare `allowed_values` for the exact supported provider values.

OAuth credential-method endpoint URLs (`authorization_url`,
`device_authorization_url`, and `token_url`) may use source-input templates, but
the rendered URLs must use HTTPS. HTTP is accepted only for localhost or
loopback development URLs, and the check runs after template expansion.

## Interfaces

Each interface has:

| Field | Required | Description |
| --- | --- | --- |
| `id` | Yes | Source-local id matching `[a-z][a-z0-9_]*`. |
| `type` | Yes | `openapi`, `mcp`, `graphql`, or `file`. |
| `inputs` | No | Interface-local input declarations. |

Interface ids become part of stable capability ids:

```text
source/<source_id>/interface/<interface_id>/operation/<operation_id>
```

## OpenAPI Interfaces

OpenAPI interfaces describe REST providers:

```yaml
interfaces:
  - id: rest
    type: openapi
    url: https://api.example.com/openapi.json
    overlays:
      - file: ./api-fixes.overlay.yaml
    base_url: https://api.example.com
    auth:
      kind: bearer_input
      key: API_TOKEN
```

Use `file:` instead of `url:` for a local descriptor:

```yaml
interfaces:
  - id: rest
    type: openapi
    file: ./openapi.yaml
```

| Field | Required | Description |
| --- | --- | --- |
| `id` | Yes | Interface id. |
| `type` | Yes | Must be `openapi`. |
| `url` | One of `url`/`file` | HTTPS OpenAPI descriptor URL or `{{input.KEY}}` URL template. Localhost HTTP is allowed for development fixtures. |
| `file` | One of `url`/`file` | Local OpenAPI descriptor file. |
| `overlays` | No | Ordered list of local OpenAPI Overlay files to apply before import. |
| `base_url` | No | Runtime provider base URL override or `{{input.KEY}}` URL template. |
| `auth` | No | Auth descriptor. |
| `inputs` | No | Interface-local inputs. |

OpenAPI `url` and `base_url` may be literal URLs or HTTPS templates using
`{{input.KEY}}` tokens. Template tokens must reference declared variable inputs,
not secrets, and must not include inline defaults. Coral validates the rendered
URL during source materialization and invocation.
For local descriptor files, `coral source add --file <manifest>` resolves
relative `file:` paths from the manifest directory before import. Direct API
imports must send absolute file paths.

Use `overlays` when the OpenAPI descriptor needs repeatable local corrections:

```yaml
interfaces:
  - id: rest
    type: openapi
    url: https://api.example.com/openapi.json
    overlays:
      - file: ./api-fixes.overlay.yaml
```

Overlay files use the OpenAPI Overlay format and are applied in declaration
order before Coral imports the effective OpenAPI document. Coral currently
supports `update` and `remove` actions with simple JSONPath targets using
dotted fields, quoted fields, array indexes, and wildcards. Overlay targets must
match at least one node. `copy` actions and JSONPath filters are not supported.
`coral source add --file <manifest>` resolves relative overlay files from the
manifest directory before import. Direct API imports must send absolute overlay
file paths.

If `auth` is configured, Coral sends it while fetching the OpenAPI `url` only
when `url` is same-origin with `base_url`. Public descriptors hosted elsewhere,
such as vendor OpenAPI files on a documentation or source-control domain, are
downloaded without provider credentials.

OpenAPI import preserves provider operation identity, parameter serialization,
request media types, response variants, security requirements, and provenance.
Supported operations become capabilities. SQL bindings are generated only when
an operation is read-like and row-shaped.

## MCP Interfaces

MCP interfaces describe upstream MCP providers. This is separate from Coral's
own MCP server.

Streamable HTTP:

```yaml
interfaces:
  - id: mcp
    type: mcp
    server:
      transport:
        type: streamable_http
        url: https://mcp.example.com/mcp
      auth:
        kind: bearer_input
        key: API_TOKEN
```

Trusted local stdio:

```yaml
interfaces:
  - id: mcp
    type: mcp
    server:
      transport:
        type: stdio
        command: github-mcp-server
        args: []
      env:
        - name: GITHUB_TOKEN
          key: API_TOKEN
```

| Field | Required | Description |
| --- | --- | --- |
| `server.transport.type` | Yes | `streamable_http` or `stdio`. |
| `server.transport.url` | For Streamable HTTP | HTTPS URL or `{{input.KEY}}` URL template. Localhost HTTP is allowed for development fixtures. |
| `server.transport.command` | For stdio | Local executable command. Coral executes it directly, not through a shell. |
| `server.transport.args` | No | Stdio argument array. |
| `server.auth` | No | Auth descriptor for Streamable HTTP. |
| `server.env` | No | Stdio environment bindings from declared inputs. |

Streamable HTTP `server.transport.url` may be a literal URL or an HTTPS
template using `{{input.KEY}}` tokens. Template tokens must reference declared
variable inputs, not secrets, and must not include inline defaults. Coral
validates the rendered endpoint during source materialization and invocation.

During materialization, Coral snapshots upstream `tools/list` and generates one
capability per supported tool. Coral maps MCP `ToolAnnotations` to effect
profiles using MCP defaults: `readOnlyHint: true` becomes a read query;
otherwise `destructiveHint` (default `true`) decides delete versus write, and
`idempotentHint` controls idempotency. Coral does not infer effects from tool
names or descriptions. `tools.listChanged` is preserved as snapshot evidence
and does not trigger background refresh in this branch.

Most MCP tools are TypeScript callable only. SQL bindings require read-like
classification plus structured, obvious row output.

## GraphQL Interfaces

GraphQL interfaces describe GraphQL providers:

```yaml
interfaces:
  - id: graph
    type: graphql
    endpoint: https://api.example.com/graphql
    auth:
      kind: bearer_input
      key: API_TOKEN
    schema:
      kind: introspection_query
```

| Field | Required | Description |
| --- | --- | --- |
| `endpoint` | Yes | GraphQL endpoint URL or `{{input.KEY}}` URL template. HTTPS is required except localhost development URLs. |
| `schema` | Yes | Schema descriptor. |
| `auth` | No | Auth descriptor for endpoint/schema fetch and invocation. |

GraphQL `endpoint` and live-introspection endpoint overrides may be literal URLs
or HTTPS templates using `{{input.KEY}}` tokens. Template tokens must reference
declared variable inputs, not secrets, and must not include inline defaults.
SDL and introspection JSON schema URLs are literal descriptor URLs.

If `auth` is configured, Coral sends it while fetching GraphQL SDL,
introspection JSON, or live introspection only when that schema acquisition URL
is same-origin with the GraphQL `endpoint`.

Schema descriptor variants:

```yaml
schema:
  kind: sdl_url
  url: https://api.example.com/schema.graphql
```

```yaml
schema:
  kind: sdl_file
  file: ./schema.graphql
```

```yaml
schema:
  kind: introspection_json_url
  url: https://api.example.com/schema.json
```

```yaml
schema:
  kind: introspection_json_file
  file: ./schema.json
```

```yaml
schema:
  kind: introspection_query
  endpoint: https://api.example.com/graphql
```

For `introspection_query`, `endpoint` is optional; Coral uses the interface
endpoint when it is omitted.

GraphQL import extracts supported root `Query` and `Mutation` fields, including
fields with arguments and object/connection return types. Coral generates
bounded operation documents with GraphQL variables, shallow scalar selections,
and connection-style `nodes`/`pageInfo` selections when the schema exposes that
shape. Root `Query` fields default to read/idempotent. Root `Mutation` fields
default to write/non-idempotent. Subscriptions are unsupported in this branch
and are preserved as diagnostics/snapshot facts.

Deprecated root GraphQL fields are preserved in the provider snapshot as
unsupported facts but are not exposed as invokable capabilities. Coral also
fails closed when a generated operation document referenced by a materialized
capability is missing or incompatible; re-add the source with the current Coral
binary to regenerate artifacts.

User-authored GraphQL operations, selection refinements, pagination profiles,
row-shape hints, and aliases are not SourceSpec fields.

## File Interfaces

File interfaces describe explicit read-only local files:

```yaml
interfaces:
  - id: messages
    type: file
    files:
      - /absolute/path/to/messages.jsonl
    format:
      kind: jsonl
```

Supported `format.kind` values:

- `json`
- `jsonl`
- `csv`
- `parquet`

File interfaces are a trust boundary. A spec names explicit files; it does not
grant agents arbitrary filesystem traversal. Generated artifacts store
source-local file refs and app-owned metadata, not arbitrary absolute paths for
MCP or Code Mode results.

Supported file read capabilities may emit both TypeScript and SQL bindings when
the file format and schema are known.

## Test Queries

`test_queries` are optional read-only SQL checks:

```yaml
test_queries:
  - SELECT * FROM my_source.messages LIMIT 1
```

Use them only for generated SQL bindings. Keep them cheap and bounded. Coral
rejects DDL, DML, multiple statements, and other non-read-only validation
queries.

## Generated Artifacts

Installed sources materialize source-scoped artifacts:

```text
artifacts.yaml
fingerprint.yaml
capabilities.yaml
exports/source-exports.yaml
diagnostics.yaml
interfaces/<interface-id>/source-document.raw
interfaces/<interface-id>/provider-snapshot.yaml
interfaces/<interface-id>/generated-graphql-operations/
```

`capabilities.yaml` is the central generated artifact. SQL projection metadata
lives in SQL bindings inside `exports/source-exports.yaml`. Query and invocation
fail closed when required generated artifacts are missing or incompatible.

## Discovery And Binding Refs

MCP agents discover generated exports with `search` and inspect them with
`describe`.

Typed refs identify usable bindings:

```text
typescript:github.rest.issues.list
sql_table:github_rest.issues
```

Capability ids remain the stable internal identity. Typed refs and TypeScript
paths are ergonomic binding names and may change under deterministic collision
handling without changing capability identity.

## MCP Error Reasons

Upstream MCP provider failures are returned as structured provider errors.
Generated Code Mode methods reject by default, and callers can use
`allowErrorResult` to collect the raw `{ ok: false }` envelope. Common reasons
include:

| Reason | Meaning |
| --- | --- |
| `protocol_error` | The upstream MCP server returned a JSON-RPC or protocol error. |
| `tool_error` | The upstream tool returned `isError: true`. |
| `tool_not_found` | The stored tool name is no longer available. |
| `output_schema_mismatch` | Tool output did not match the imported output schema. |
| `transport_error` | Coral could not reach or communicate with the upstream MCP server. |
| `unsupported` | The imported capability exists, but this runtime cannot invoke that transport or shape yet. |

Provider output is untrusted. Coral preserves structured content and content
blocks in the raw invocation envelope, but it does not follow resource links or
embedded resources automatically. For the successful invocation `value`, Coral
uses MCP `structuredContent` when present. If the provider omits
`structuredContent` and returns a single text content block containing exact
JSON, Coral parses that JSON into `value`; otherwise the text content stays
text. Provider error details are bounded before they leave the provider runtime;
HTTP failures include status and a body preview when available, and MCP failures
include JSON-RPC or tool-result details when available.
