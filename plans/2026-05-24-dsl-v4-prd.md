# Coral Source DSL v4 PRD (Surface-First Projection IR)

## Summary

Coral source specs currently use a table-oriented authoring model. A source
manifest chooses one top-level `backend` and then hard-codes the SQL surfaces
that Coral exposes through `tables:` and `functions:`. For HTTP sources, those
same table/function entries also declare provider request details, response
extraction, filters, arguments, columns, and pagination.

That model works for curated, hand-authored sources, but it does not scale to
providers that already publish authoritative API descriptions such as OpenAPI or
GraphQL schemas. It also forces a source to be represented by one implementation
surface even when a real provider exposes several useful surfaces, such as
GitHub REST and GitHub GraphQL.

DSL v4 introduces a surface-first source model:

1. The manifest declares one or more upstream surfaces and how to call them.
2. Coral imports each surface description into a stable semantic IR.
3. Coral generates SQL projections from that IR by default.
4. Runtime execution remains surface-specific. The IR is a projection substrate,
   not a generic physical executor abstraction.

The core design split is:

- **Surface type** answers how Coral talks to the provider: OpenAPI/REST,
  GraphQL, MCP, file scan, or a future protocol.
- **Semantic IR** answers what capabilities the provider exposes in a normalized
  vocabulary that projection generation can use.
- **Projection catalog** answers what SQL tables/functions Coral publishes.
- **Physical planners** answer how a projection is executed for one concrete
  surface type.

The first implementation wave is OpenAPI-first. A v4 manifest can declare
OpenAPI surfaces, Coral imports pinned OpenAPI descriptions during source add,
materializes a semantic IR plus generated projection catalog to local app state,
and later loads the installed source without network access or re-importing the
OpenAPI document.

Current `dsl_version: 3` manifests remain supported unchanged.

## Goals

- Add DSL v4 manifests that declare API surfaces instead of hard-coded
  `tables:` and `functions:` arrays.
- Remove top-level `backend` from v4 manifests. Runtime implementation type is
  declared per surface.
- Import a stable semantic IR from provider-supplied OpenAPI descriptions.
- Use the semantic IR as the common substrate for automatic SQL projection
  generation.
- Keep generated projections deterministic and useful without requiring authors
  to inspect generated IR before install.
- Keep input declarations on the surface that uses them. At source add time,
  Coral prompts for the union of inputs required by all surfaces in the source.
- Materialize imported IR and generated projections to local app state during
  source add so normal query-time loads do not fetch or parse upstream
  descriptions.
- Preserve v3 parser, schema, install, and runtime behavior during migration.
- Execute a narrow GitHub issues slice end to end through a v4 OpenAPI surface.
- Keep the implementation aligned with current crate boundaries: source-spec
  parsing in `coral-spec`, app-state materialization in `coral-app`, and
  physical execution in `coral-engine`.

## Non-Goals for this wave

- Convert existing v3 manifests automatically.
- Replace the existing v3 HTTP, JSONL, or Parquet backends.
- Add a full GraphQL importer or GraphQL executor. The IR must leave room for a
  GraphQL fast-follow, but this wave ships OpenAPI execution only.
- Expose mutating operations as SQL affordances. Coral remains read-only for
  generated projections in this wave.
- Infer canonical cross-surface entity identity. Imported entity candidates are
  useful evidence for projection generation, not proof that two surfaces model
  the same logical provider object.
- Build a complete source-authoring UI or broad projection editor.
- Solve every naming, table-vs-function, search ranking, or relationship
  heuristic. The first implementation must be deterministic, documented, and
  explicit about unsupported cases.
- Add projection overrides to the source manifest. Projection overrides remain
  deferred because manifest-authored overrides would require authors to generate
  IR first, inspect imported operation/type names, and then edit the manifest
  that produced that IR.

## Explicit Anti-Goals

- **Do not hand-author provider operations in v4 manifests.** A v4 manifest must
  not declare provider paths, methods, parameter mappings, response paths, or
  pagination details for imported OpenAPI operations. Those facts come from the
  upstream API description and importer.
- **Do not make the semantic IR the physical executor abstraction.** The engine
  must still know whether a projection resolves to REST/OpenAPI, GraphQL, MCP,
  or another surface type when it builds a physical plan.
- **Do not require normal source authors to inspect generated IR before a source
  can be installed.** Projection generation must have useful defaults.
- **Do not put projection overrides in the v4 source manifest.** This creates a
  chicken-and-egg authoring loop because the override author needs generated IR
  names and types before the source can be finalized. Projection overrides may
  return later as a separate artifact outside the source manifest.
- **Do not add a synthetic top-level backend for v4.** In v4, `dsl_version`
  selects the v4 manifest shape and each surface declares its own `type`. There
  is no top-level `backend` field in the v4 schema.

The only opinionated authoring surfaces in a v4 manifest are:

- the existing source identity/install envelope (`name`, `version`,
  `dsl_version`, `description`, and test queries),
- `surfaces:` for upstream descriptions, surface-scoped input declarations, and
  surface runtime configuration,
- optional `projection_policy:` for broad generation behavior.

## DSL v4 Manifest Boundary

DSL v4 keeps the current source identity/install envelope, but replaces
top-level `backend`, `base_url`, `auth`, `request_headers`, `rate_limit`,
`tables`, `functions`, and source-level `inputs` with surface declarations.

First-wave manifest shape:

```yaml
name: github
version: 2.0.0
dsl_version: 4
description: >-
  Query GitHub issues through imported provider API descriptions.

test_queries:
  - SELECT * FROM github.issues WHERE owner = 'octocat' AND repo = 'Hello-World' LIMIT 1

surfaces:
  - id: rest
    type: openapi
    url: https://raw.githubusercontent.com/github/rest-api-description/<commit>/descriptions/api.github.com/api.github.com.yaml
    sha256: 7f2a...
    inputs:
      GITHUB_API_BASE:
        kind: variable
        default: https://api.github.com
      GITHUB_TOKEN:
        kind: secret
    base_url: "{{input.GITHUB_API_BASE}}"
    auth:
      type: HeaderAuth
      headers:
        - name: Authorization
          from: template
          template: Bearer {{input.GITHUB_TOKEN}}
    request_headers:
      - name: Accept
        from: literal
        value: application/vnd.github+json
      - name: X-GitHub-Api-Version
        from: literal
        value: "2022-11-28"
    rate_limit:
      extra_statuses: [403]
      remaining_header: x-ratelimit-remaining
      reset_header: x-ratelimit-reset

projection_policy:
  default: derive_read_operations
```

First-wave surface descriptors are mutually exclusive:

```yaml
# Remote, production-supported descriptor.
url: https://example.com/openapi.yaml
sha256: 7f2a...

# Local descriptor. Imported sources resolve this under the current working
# directory. Bundled v4 sources may use manifest-local relative paths when the
# release build embeds descriptor bytes.
file: openapi.yaml
sha256: 7f2a...
```

Remote descriptors must use `https`. Imported local `file` descriptors must be
regular files under the current working directory and must not be symlinks.
Bundled v4 `file` descriptors are allowed only when the build embeds the
referenced descriptor bytes into the binary; query-time materialization then
uses those embedded bytes instead of reading from the release user's
filesystem.

Author-facing changes versus v3:

- Remove top-level `backend` from v4.
- Remove top-level HTTP runtime configuration. Runtime API configuration lives
  on the surface that uses it.
- Remove authored `tables:` and `functions:` from v4.
- Add `surfaces:` as the authoritative list of imported provider surfaces.
- Generate SQL projections from imported IR by default.
- Add optional projection policy for broad generation behavior.
- Move `inputs` from the source level to the surface level. Credentials and
  install-time variables are declared by each surface that uses them; `source
  add` prompts for the union of all surface input declarations.

DSL v4 is additive. Existing `dsl_version: 3` manifests keep their current
schema, including top-level `backend`, `tables`, and `functions`.

### Manifest Schema Rules

Allowed top-level v4 fields are:

- `name`,
- `version`,
- `dsl_version`,
- `description`,
- `test_queries`,
- `onboarding`,
- `surfaces`,
- `projection_policy`.

V4 rejects these top-level fields:

- `backend`,
- `base_url`,
- `auth`,
- `request_headers`,
- `rate_limit`,
- `inputs`,
- `tables`,
- `functions`,
- `projection_overrides`.

`dsl_version` must be `4`. `surfaces` is required and must contain at least one
entry. `projection_policy.default` is optional and, when present, must be
`derive_read_operations`; any other value is rejected in this wave.

Each surface entry must contain:

- `id`: `[a-z][a-z0-9_]*`, unique within the source,
- `type`: `openapi`,
- exactly one descriptor location, either `url` or `file`,
- `sha256`: lowercase hex SHA-256 of the exact descriptor bytes,
- optional `inputs`,
- runtime configuration fields supported by the surface type.

For `type: openapi`, runtime configuration fields are `base_url`, `auth`,
`request_headers`, and `rate_limit`. Those fields reuse the existing v3 HTTP
shapes where the shape is already source-spec-neutral, but they are nested under
the surface and must not be parsed into `HttpSourceManifest`.

For `type: openapi`, `base_url` is required and must be a non-empty
`ParsedTemplate`. `auth`, `request_headers`, and `rate_limit` default to the
existing v3 HTTP defaults: empty `HeaderAuth`, empty headers, and default
`RateLimitSpec`. OpenAPI `servers` are ignored for runtime base URL selection in
this wave.

Unknown fields are rejected at the top level and inside surfaces. Duplicate
surface IDs, duplicate operation IDs after normalization, duplicate projection
names after collision resolution, and incompatible repeated input declarations
are validation errors.

## Surfaces and Importers

A surface entry tells Coral where to find an upstream API description, which
importer to apply, and how to call that upstream surface at runtime.

Surface entries also declare the inputs that surface needs. Source add must
collect the union of all surface input declarations and prompt once for each
logical input. Reusing the same input name across surfaces is valid only when
the declarations are compatible; conflicting declarations are a manifest
validation error unless a later spec adds explicit namespacing or aliasing.

For the first wave, compatibility is exact structural equality over the current
input declaration contract:

- `kind`,
- `required`,
- variable `default`,
- `hint`,
- secret `credential.methods` including authored order and OAuth settings.

The computed union is still exposed to the existing app, API, and CLI surfaces as
one flat source input list in stable order. V4 does not add public surface-scoped
input APIs in this wave. Runtime execution filters that flat binding map to the
inputs declared by the surface that owns the selected projection.

First-wave supported surface type:

- `type: openapi`

Reserved future surface types:

- `type: graphql`
- `type: mcp`

Reserved surface types are rejected until their importers and runtime planners
exist. The first wave supports multiple `openapi` surfaces in one manifest for
both materialization and execution.

The OpenAPI importer:

1. Resolves the description from a pinned descriptor (`url` plus `sha256`, or a
   local development file with equivalent hash validation).
2. Parses the OpenAPI document.
3. Produces a semantic IR with normalized operations, inputs, output shapes,
   entity candidates, relationships, cardinality, and surface-specific
   execution attachments.
4. Generates a projection catalog from the semantic IR.
5. Writes materialized artifacts to app state during source add.

The semantic IR is intentionally not a public authoring format. It is an
internal, stable-enough artifact for projection generation, validation, and
query-time runtime loading.

### Surface Document Pinning

OpenAPI source documents must be reproducible. Two users installing the same
manifest must import the same provider description and generate the same default
projections.

- A surface descriptor must provide a retrieval location and a content hash.
- The retrieval location does not need to be immutable; `sha256` is the
  reproducibility contract.
- If fetched bytes do not match `sha256`, source add fails.
- Bundled/core sources should prefer provider-owned immutable URLs when they
  exist.
- When a provider does not offer an immutable historical OpenAPI URL, Coral
  should mirror the exact OpenAPI artifact at a Coral-owned artifact URL and pin
  that URL with `sha256`.
- User-installed/community sources may use mutable provider URLs, but they must
  still provide `sha256`.

There is no unpinned URL mode.

### Surface IDs and Operation IDs

Surface IDs are manifest-authored and source-local. They are used by
materialized artifacts and runtime diagnostics. They must be stable across
source versions unless the surface is intentionally replaced.

Operation IDs are imported and surface-scoped:

- If an OpenAPI operation has `operationId`, use it after minimal YAML-safe
  normalization. Normalization preserves ASCII letters and numbers, converts
  other runs to `_`, trims leading/trailing `_`, lowercases the result, and
  prefixes `operation_` if the result would be empty or start with a digit.
- If `operationId` is absent, generate a deterministic ID from method and path
  using `<method>_<normalized_path>`, where path parameters lose braces. For
  example, `GET /repos/{owner}/{repo}/issues` becomes
  `get_repos_owner_repo_issues`.
- Duplicate operation IDs within one surface are a hard import error.

Generated projection entries reference imported operations by `(surface,
operation)`.

## Semantic IR Requirements

The semantic IR is the normalized contract between importers and projection
machinery. It exists so projection generation can treat heterogeneous surfaces
with one vocabulary. It does not erase protocol-specific execution details.

The IR must represent:

- surfaces and their type,
- operations scoped to one surface,
- operation inputs and whether they are required,
- normalized scalar/object/list/map/enum/type shapes,
- output cardinality: none, singleton, list, wrapped list, or unknown,
- entity candidates scoped to their importing surface,
- relationship hints where they are discoverable,
- identity key evidence where it is discoverable,
- pagination capability and result-window limits,
- deprecation and description metadata,
- protocol-specific execution attachments needed by physical planners.

The first-wave OpenAPI importer must include REST execution attachments for:

- HTTP method,
- path template,
- path/query/header/cookie parameter serialization,
- request body shape,
- response status/media-type behavior,
- row extraction for list and wrapped-list responses,
- pagination behavior sufficient for the GitHub issues slice,
- surface-local error metadata where needed.

The first-wave OpenAPI subset is intentionally narrow and deterministic:

- Implement the importer with a Coral-owned minimal serde model for the supported
  subset rather than depending on a broad OpenAPI crate for behavior. A future
  dependency can replace that parser only if it preserves these documented import
  semantics.
- OpenAPI 3.0.x documents only.
- YAML and JSON source documents.
- Internal `$ref` references only; external references hide the referencing
  operation with diagnostics.
- `allOf` object composition is supported by deterministic object-property
  merge. Conflicting scalar/object definitions hide the operation with
  diagnostics.
- `oneOf` and `anyOf` are unsupported except for trivial nullable wrappers. A
  trivial nullable wrapper is exactly one supported schema plus exactly one
  `type: "null"` schema or an OpenAPI 3.0 schema with `nullable: true`. Other
  uses hide the operation with diagnostics.
- Only `application/json` responses are imported for published projections.
- Response selection chooses the first successful 2xx JSON response, preferring
  explicit `200` when present.
- Path, query, header, and cookie parameters are supported only for primitive
  scalar values and arrays with OpenAPI default form serialization. Unsupported
  serialization hides the operation with diagnostics.
- Request-body operations are imported as IR evidence but are not published by
  the default projection policy.
- Pagination support is limited to GitHub-style `Link` headers and `page` /
  `per_page` query parameters in this wave.

### OpenAPI Import Algorithm

The importer must process one OpenAPI document in this order:

1. Parse YAML/JSON into the Coral-owned OpenAPI subset model.
2. Validate `openapi` starts with `3.0.`.
3. Build an internal reference index from all local JSON pointers in
   `#/components/schemas`, `#/components/parameters`, and
   `#/components/responses`.
4. Walk paths in source-document order, then methods in this order: `get`,
   `head`, `options`, `post`, `put`, `patch`, `delete`, `trace`.
5. Resolve operation-level parameters after path-level parameters. Operation
   parameters with the same `(location, name)` replace path-level parameters.
6. Import every operation into IR evidence unless the document is malformed
   enough to prevent deterministic import.
7. Generate diagnostics for every unsupported feature and mark affected
   operations hidden rather than silently dropping them.

Reference resolution:

- Only local references beginning with `#/` are supported.
- References are resolved depth-first with cycle detection. A reference cycle
  hides every operation whose input or output depends on the cycle.
- Missing references hide dependent operations with diagnostic code
  `OPENAPI_REF_NOT_FOUND`.
- External references hide dependent operations with diagnostic code
  `OPENAPI_EXTERNAL_REF_UNSUPPORTED`.

Schema handling:

- `allOf` merges object schemas in listed order. Object properties are appended
  in first-seen order. Later definitions of the same property are allowed only
  when the resolved schema is structurally identical; otherwise the dependent
  operation is hidden with `OPENAPI_ALLOF_CONFLICT`.
- A trivial nullable wrapper is `oneOf` or `anyOf` with exactly two variants,
  where one variant is `{ "type": "null" }` and the other variant is a supported
  schema, or an OpenAPI 3.0 schema with `nullable: true`. The result is the
  supported schema with `nullable: true`.
- Other `oneOf`/`anyOf` uses map to `Json` for nested columns, but hide the
  operation when they determine operation input, response cardinality, or row
  extraction.
- `required` controls object-field requiredness only. Column nullability remains
  nullable for generated SQL columns in this wave.

Response and row extraction:

- Candidate responses are explicit 2xx responses with `application/json`
  content. If status `200` exists it wins; otherwise choose the lowest numeric
  2xx status in source order. `default` responses are diagnostics only.
- A top-level array response has `cardinality: List` and `row_path: []`.
- A top-level object response with property `items` whose schema is an array has
  `cardinality: WrappedList` and `row_path: ["items"]`.
- Other top-level object responses have `cardinality: Singleton` and
  `row_path: []`.
- Empty or no-body 2xx responses have `cardinality: None` and are imported as
  non-published IR evidence.
- Unknown response shapes have `cardinality: Unknown` and hidden projections.
- REST response attachments must store a `ResponseSpec` equivalent to the row
  path: direct rows for `[]`, `rows_path: ["items"]` for wrapped lists.

Pagination detection:

- If the operation accepts `page` and `per_page` query parameters, emit page
  pagination using those parameter names.
- If the response documents or runtime surface uses GitHub-style `Link` headers,
  emit link-header pagination.
- If both are present, prefer GitHub-style `Link` headers for execution and keep
  `page`/`per_page` as optional SQL inputs when they are OpenAPI parameters.
- Unsupported pagination leaves the projection published only when a single
  request is still useful; otherwise hide it with `OPENAPI_PAGINATION_UNSUPPORTED`.

| Operation | Imported operation ID | Cardinality | Row path | Published |
|---|---|---:|---|---|
| List repository issues | `issues/list-for-repo` normalized to `issues_list_for_repo` | List | `[]` | yes |
| Search issues | `search/issues-and-pull-requests` normalized to `search_issues_and_pull_requests` | WrappedList | `items` | yes |

The IR must be serialized to the human-inspectable
`materialized/v4/surfaces/<surface-id>/semantic-ir.yaml` artifact. The artifact
is internal and may evolve only when `artifact_schema_version` or
`importer_version` changes.

### Types

Support:

- scalar types: string, integer, float/number, boolean, ID, timestamp/date-time,
  URI/string-like provider scalars, JSON/any, null,
- enums and constrained values,
- object types,
- input object types,
- arrays/lists,
- maps/dictionaries,
- nullable vs optional semantics,
- descriptions and deprecation metadata.

The IR must reserve fields or enum extension points so interfaces, unions, field
arguments, and GraphQL connection-like output can be added without forcing a
wholesale replacement of the projection generator.

### Entities and Identity

Entities in first-wave IR are imported, surface-scoped entity candidates. They
are useful for projection generation, column naming, detail hints, and future
relationship handling.

The importer must not automatically assert that an entity imported from one
surface is equivalent to an entity imported from another surface. For example,
a future GitHub REST `issue` entity and GitHub GraphQL `Issue` entity may
represent the same provider concept, but that equivalence requires explicit
curation in a later wave.

Identity keys are evidence. They may be represented in IR, but first-wave
runtime planning does not perform cross-surface identity lookups.

## Projection Generation

Projection generation turns semantic IR into the SQL catalog Coral exposes.

Default policy for this wave:

```yaml
projection_policy:
  default: derive_read_operations
```

If `projection_policy` is absent, the default is `derive_read_operations`.

The default generator must:

- consider only read-only operations,
- expose supported OpenAPI `GET` operations,
- skip mutating methods and request-body operations unless a later explicit
  policy supports them,
- derive a stable SQL name from operation/entity metadata,
- derive table columns from the operation output shape,
- derive required filters or function arguments from required operation inputs,
- derive pagination settings from imported surface metadata,
- generate a table for list-like and singleton readable resources when inputs
  can be represented as filters,
- generate a table function for search-like or operation-like reads when
  function arguments are the better SQL affordance,
- hide unsupported or unsafe operations by default with diagnostics.

Projection naming and shape are part of the first-wave SQL contract:

- SQL identifiers are normalized to lowercase snake_case ASCII. Runs of
  unsupported characters become `_`; leading/trailing `_` are removed; names that
  would be empty or start with a digit are prefixed with `projection_` or
  `column_` as appropriate.
- Projection-name collisions are resolved by appending
  `__<8-char-stable-hash>`, where the hash input is
  `<source-name>/<surface-id>/<operation-id>`.
- Column names follow the same normalization. Column-name collisions in one
  projection receive the same stable-hash suffix using the full source field
  path as hash input.
- Object response top-level scalar fields become columns.
- Nested objects, arrays, maps, unknown shapes, unsupported unions, and
  provider-specific extension values become JSON columns.
- Column order follows the resolved OpenAPI schema property order.
- All generated columns are nullable in this wave.
- OpenAPI `string` with `format: date-time` maps to Timestamp; integer maps to
  Int64; number maps to Float64; boolean maps to Boolean; enums map to Utf8;
  unrecognized scalar formats map to Utf8.

Projection kind selection is deterministic:

1. Unsupported, mutating, request-body, no-body, unknown-cardinality, or
   ambiguous operations become hidden projections with diagnostics.
2. Search detection runs before generic list/table selection. An operation is
   search-like when its normalized operation ID or normalized path contains the
   token `search` and its response is list-like. Search-like operations become
   table functions with `kind: search`.
3. List or wrapped-list responses become SQL tables when all required operation
   inputs can be represented as filters.
4. Singleton responses with required operation inputs become table functions with
   existing `kind: table` semantics and generated `get_*` names.
5. Singleton responses with no required operation inputs become SQL tables.

For the GitHub acceptance slice this means repository issues are generated as an
`issues` table with required `owner` and `repo` filters, search issues as a
`search_issues` table function with `kind: search`, and get issue as a
`get_issue` table function with `kind: table`.

Projection naming is deterministic:

Entity candidate names are derived before projection naming:

1. Prefer the final component of the resolved OpenAPI response schema `$ref`.
2. Otherwise use schema `title`.
3. Otherwise use the last non-parameter path segment for singleton/list
   operations.
4. For search operations, use the wrapped-list item schema name when available;
   otherwise use the final search path segment.
5. Normalize the entity candidate with the SQL identifier rules. Singular/plural
   conversion is deliberately minimal: remove one trailing `s` only when the
   operation is singleton and the candidate ends with `s`; add `s` only when the
   operation is list-like and the candidate does not already end with `s`.

Projection names are then selected in this order:

1. If the operation has an entity candidate and list-like response, use the
   normalized plural entity name. For GitHub repository issues, this yields
   `issues`.
2. If the operation is search-like, prefix the normalized singular/plural entity
   name with `search_`. For GitHub search issues, this yields `search_issues`.
3. If the operation is singleton with required inputs, prefix the normalized
   entity name with `get_`. For GitHub get issue, this yields `get_issue`.
4. Otherwise use the normalized operation ID.
5. Apply collision suffixing after the preferred name is selected.

Expected first-wave generated GitHub projections:

| Projection | Kind | Operation | Required SQL inputs | Optional SQL inputs | Minimum columns | Pagination | Visibility |
|---|---|---|---|---|---|---|---|
| `issues` | table | `issues_list_for_repo` | filters `owner`, `repo` | filters `state`, `labels`, `sort`, `direction`, `since`, `page`, `per_page` when present in OpenAPI | `id`, `number`, `title`, `state`, `html_url`, `created_at`, `updated_at`, `user` JSON | Link or page/per_page | published |
| `search_issues` | table function `kind: search` | `search_issues_and_pull_requests` | arg `q` | args `sort`, `order`, `page`, `per_page` when present in OpenAPI | `id`, `number`, `title`, `state`, `html_url`, `repository_url`, `user` JSON | Link or page/per_page | published |
| `get_issue` | table function `kind: table` | `issues_get` | args `owner`, `repo`, `issue_number` | none unless present in OpenAPI | `id`, `number`, `title`, `state`, `html_url`, `body`, `user` JSON | none | published |

### SQL Input Mapping

OpenAPI inputs map to SQL inputs by operation kind:

| OpenAPI input | Table projection | Table-function projection | Required/default behavior | Runtime error |
|---|---|---|---|---|
| path parameter | required filter | required arg | always required; no default | missing required filter/arg names projection, surface, operation, and parameter |
| query parameter, required | required filter | required arg | required unless OpenAPI default exists; default fills absent SQL input | same as above when no default |
| query parameter, optional | optional filter | optional arg | omitted when absent; OpenAPI default used when declared | none |
| header/cookie parameter declared in OpenAPI | internal input when satisfiable from surface config/request headers/auth; otherwise hidden operation | same | required values must come from surface runtime config, not SQL | hidden operation diagnostic, not runtime prompt |
| request body | hidden operation | hidden operation | request-body operations are not published | hidden operation diagnostic |

Generated table filters use existing `FilterSpec` semantics with `mode:
equality`. Generated table-function args use existing `TableFunctionArgSpec`
semantics. Generated SQL input types map from OpenAPI scalar types through the
same scalar mapping used for columns. Arrays, objects, and unsupported parameter
schemas hide the operation unless the parameter is optional and can be ignored.

Concrete GitHub input examples:

| Input | OpenAPI location | Generated SQL exposure |
|---|---|---|
| `owner` | path | required `issues` filter; required `get_issue` arg |
| `repo` | path | required `issues` filter; required `get_issue` arg |
| `issue_number` | path | required `get_issue` arg |
| `q` | query | required `search_issues` arg |
| `page` | query | optional filter/arg when present in OpenAPI |
| `per_page` | query | optional filter/arg when present in OpenAPI |

Projection overrides are not part of the v4 manifest in this wave. Any future
override mechanism must live outside the source manifest so authors can first
import a source, inspect materialized IR/projection artifacts, and then author
curation against those generated names and types.

Materialized projection catalog entries must be normalized into a runtime-ready
shape with these fields:

- SQL table or table-function name,
- description and guide,
- surface ID,
- operation ID,
- generated provenance and diagnostics,
- input exposure model,
- output columns,
- pagination/fetch-limit behavior,
- search limits and detail hints,
- visibility status,
- link to protocol-specific execution attachment.

The runtime must consume the materialized projection catalog rather than
regenerating projections at query time.

## Materialization and App State

Source add is the materialization boundary.

For a v4 source, `coral source add` or imported source add must:

1. Parse and validate the manifest.
2. Validate surface input declarations.
3. Compute the union of input declarations across all surfaces and collect user
   bindings once per compatible logical input.
4. Persist input bindings through the existing source-scoped app/API model, with
   secrets remaining secret material and variables remaining non-secret config.
   Surface-specific input ownership is stored in the manifest/materialized
   artifacts, not in public source state.
5. For each surface, fetch/read the pinned upstream description.
6. Verify the content hash.
7. Import semantic IR.
8. Generate default projections.
9. Validate generated projections against the IR.
10. Write materialized artifacts under the existing source app-state directory.
11. Persist source config, credential material, and materialized artifacts only if
    materialization succeeds.

Normal query-time source loading must:

- resolve the manifest using the existing bundled/imported source rules,
- read materialized v4 artifacts from app state,
- validate lookup keys and importer version,
- fail clearly if required artifacts are missing or stale,
- avoid network access,
- avoid re-fetching upstream descriptions,
- avoid re-running importers or projection generation.

App-state paths:

```text
workspaces/<workspace>/sources/<source>/manifest.yaml
workspaces/<workspace>/sources/<source>/secrets.env
workspaces/<workspace>/sources/<source>/materialized/v4/fingerprint.yaml
workspaces/<workspace>/sources/<source>/materialized/v4/diagnostics.yaml
workspaces/<workspace>/sources/<source>/materialized/v4/projections.yaml
workspaces/<workspace>/sources/<source>/materialized/v4/surfaces/<surface-id>/semantic-ir.yaml
workspaces/<workspace>/sources/<source>/materialized/v4/surfaces/<surface-id>/source-document.raw
workspaces/<workspace>/sources/<source>/materialized/v4/surfaces/<surface-id>/source-document.yaml
```

Bundled sources still resolve their manifest from the bundled catalog, but their
materialized artifacts live under the same installed source directory after
source add.

Materialized artifacts are looked up by:

- workspace,
- source name,
- source version,
- manifest fingerprint,
- surface descriptors including input declarations, URL, and `sha256`,
- importer version,
- projection generator version.

Changing any of those materialization inputs makes the old materialization
invalid for normal load. The error should point users to reinstall or refresh
the source.

`fingerprint.yaml` is the canonical stale-check contract. It must include:

- materialized artifact schema version,
- source name and source version,
- SHA-256 of the exact raw manifest YAML used for materialization,
- normalized surface descriptors excluding secret values,
- each fetched/read source document SHA-256,
- importer version,
- projection generator version.

`source-document.raw` stores the exact fetched bytes whose hash matched the
manifest. `source-document.yaml` stores Coral's normalized parsed copy for human
inspection and debugging. Query-time loading validates `fingerprint.yaml` before
building engine state and must not fall back to importer execution.

### Source Add Transaction Sequence

V4 source add/import must be rollback-safe and must not leave an installed source
whose required materialized artifacts are absent.

Imported source sequence:

1. Parse and validate the manifest YAML.
2. Compute the flat input union and validate provided bindings/OAuth retrievals
   using the existing source input flow.
3. Build temporary credential material in memory. Do not write credentials yet.
4. Fetch/read all pinned surface descriptions into a temporary materialization
   directory under the source directory, using a unique suffix such as
   `materialized/v4.tmp.<nonce>`.
5. Verify every descriptor hash.
6. Import semantic IR, generate projections, write diagnostics, and validate all
   materialized artifacts in the temporary directory.
7. Load previous source rollback state using the existing source manager
   rollback pattern.
8. Persist the imported `manifest.yaml` when the source origin is imported.
9. Persist credential material and source variables through the existing
   source-scoped source state.
10. Atomically rename the temporary materialization directory into
    `materialized/v4`, replacing any previous v4 materialization only after the
    new one is complete.
11. Upsert the installed source catalog entry.
12. On any failure after step 7, restore the previous manifest, credentials,
    source catalog entry, and previous `materialized/v4` directory. Remove the
    temporary materialization directory.

Bundled source sequence is identical except it resolves the manifest from the
bundled catalog and does not write `manifest.yaml`. Bundled/core sources reject
local `file` descriptors before any network or credential work.

Refresh sequence:

1. Resolve the installed source and manifest.
2. Reject `dsl_version: 3` with `FAILED_PRECONDITION` and message
   `source '<name>' does not use DSL v4 materialization`.
3. Re-fetch/re-read pinned descriptors into `materialized/v4.refresh.<nonce>`.
4. Verify descriptor hashes, import IR, generate projections, write diagnostics,
   and validate the temporary artifacts.
5. Atomically replace `materialized/v4` only after all surfaces pass.
6. Leave manifest, source variables, and credential material unchanged.
7. On failure, remove the refresh temp directory and leave existing artifacts
   intact.

### Refresh

Add a user-facing refresh path:

```text
coral source refresh <source>
```

Refresh must:

- read the installed source manifest,
- re-fetch pinned surface descriptions,
- verify they still match manifest `sha256`,
- import into a temporary materialization directory,
- regenerate and validate projections,
- atomically replace materialized artifacts only after all surfaces pass.

If fetched bytes do not match the manifest hash, refresh fails and reports the
observed hash. It must not silently update the manifest pin.

Refresh does not run source `test_queries` and must not call provider data
endpoints other than the pinned description URLs/files. Users validate provider
queryability separately with the existing source validation/test path.

The app/API surface is a unary refresh operation:

```proto
rpc RefreshSource(RefreshSourceRequest) returns (RefreshSourceResponse);
```

The response returns the installed `Source` plus a materialization summary and
diagnostics. Streaming progress is deferred until refresh has real long-running
progress states that callers need to observe.

Concrete proto shape:

```proto
message RefreshSourceRequest {
  Workspace workspace = 1;
  string name = 2;
}

message RefreshSourceResponse {
  Source source = 1;
  SourceMaterializationSummary materialization = 2;
  repeated SourceMaterializationDiagnostic diagnostics = 3;
}

message SourceMaterializationSummary {
  string source_name = 1;
  string source_version = 2;
  string manifest_sha256 = 3;
  string importer_version = 4;
  string projection_generator_version = 5;
  uint32 surface_count = 6;
  uint32 projection_count = 7;
  uint32 published_projection_count = 8;
  uint32 hidden_projection_count = 9;
}

message SourceMaterializationDiagnostic {
  string code = 1;
  string severity = 2; // info, warning, error
  string message = 3;
  string surface_id = 4;
  string operation_id = 5;
  string projection_name = 6;
}
```

CLI contract:

```text
coral source refresh <source>
coral source refresh <source> --json
```

Human output prints one summary line and then warning/error diagnostics:

```text
Refreshed source github: 1 surface, 3 published projections, 42 hidden projections
warning OPENAPI_EXTERNAL_REF_UNSUPPORTED rest issues_update: external references are unsupported
```

`--json` emits one object with `source`, `materialization`, and `diagnostics`
matching the proto response fields.

Refresh error behavior:

| Condition | Status/code | Message requirement |
|---|---|---|
| source is not installed | `NOT_FOUND` | names the source |
| installed source is v3 | `FAILED_PRECONDITION` | says source does not use DSL v4 materialization |
| descriptor hash mismatch | `FAILED_PRECONDITION` | includes expected and observed SHA-256 |
| descriptor fetch/read failure | `UNAVAILABLE` for remote, `FAILED_PRECONDITION` for local file | includes descriptor location |
| importer/generator validation failure | `FAILED_PRECONDITION` | includes first diagnostic code and artifact remains unchanged |
| filesystem atomic replace failure | `INTERNAL` | existing materialization remains unchanged when possible |

## Runtime Requirements

DSL v4 adds a new runtime path beside existing v3 backend dispatch.

Target path:

```text
DSL v4 installed source
  -> resolve manifest + materialized IR + projection catalog
  -> validate materialization fingerprint
  -> compile projection catalog
  -> dispatch each projection to a surface-specific physical planner
  -> register DataFusion tables/functions
```

The first physical planner is OpenAPI/REST. It must reuse existing HTTP
runtime pieces when the reusable type does not expose v3 authoring concepts as
part of the v4 contract:

- surface variables and secrets,
- header auth and custom auth shapes,
- request headers,
- rate-limit handling,
- JSON fetch and row conversion helpers,
- pagination helpers,
- DataFusion table/table-function registration patterns.

The v4 runtime must not require the existing `HttpSourceManifest` table/function
authoring shape. Reuse helpers, not the v3 manifest model as the v4 contract.

The app-to-engine handoff must carry materialized v4 state explicitly rather
than hiding it inside the parsed manifest. Extend the query-source contract with
these fields:

```rust
QuerySource {
    source_spec: ValidatedSourceManifest,
    v4_materialization: Option<V4MaterializedSource>,
    variables,
    secrets,
}
```

`coral-app` is responsible for resolving and validating the materialized
artifacts before constructing a v4 `QuerySource`. `coral-engine` is responsible
for compiling the materialized projection catalog into DataFusion registrations
and dispatching each projection to the OpenAPI/REST physical planner. Multiple
OpenAPI surfaces in one source must execute in this wave; projection entries
carry `surface_id` so runtime lookup can select the right surface configuration
and operation attachment.

### Query-Time Failure Policy

V3 query-source loading keeps the existing behavior: most broken sources are
warned and skipped during workspace-wide query-source loading, while credential
unavailability remains a hard failure.

V4 materialization failures are hard failures. If an installed v4 source has
missing artifacts, a stale `fingerprint.yaml`, invalid materialized YAML, or a
missing `V4MaterializedSource` payload, `coral-app` must return
`FAILED_PRECONDITION` before engine compilation. It must not silently skip the
source, because skipping would make generated tables disappear from catalog and
query results.

Required behavior by operation:

| Operation | Missing/stale v4 materialization behavior |
|---|---|
| `list_catalog` | fail the whole request with `FAILED_PRECONDITION` naming the source and refresh/reinstall action |
| `list_tables` | same as `list_catalog` |
| `execute_sql` | same as `list_catalog`, even if the SQL might not reference that source, because current loading is workspace-wide |
| `explain_sql` | same as `execute_sql` |
| `validate_source <source>` | fail that source validation with `FAILED_PRECONDITION`; do not run test queries |
| `source refresh <source>` | attempt to rebuild artifacts; stale/missing old artifacts are not a precondition failure for refresh |

The required user-facing message shape is:

```text
source '<source>' has stale or missing DSL v4 materialized artifacts: <detail>. Run `coral source refresh <source>` or reinstall the source.
```

- `ValidatedManifestKind::V4(Box<V4SourceManifest>)`,
  `ValidatedSourceManifest::as_v4()`, and
  `ValidatedSourceManifest::dsl_version()` exist.
- `dsl_version: 3` still requires top-level `backend`.
- `dsl_version: 4` rejects top-level `backend`, source-level `inputs`,
  `tables`, `functions`, and `projection_overrides`.
- `dsl_version: 4` requires at least one surface.
- Schema errors identify malformed surfaces and surface input declarations
  clearly.

### 4. Semantic IR

- Add serde-friendly IR structs/enums.
- Round-trip representative REST model fragments.
- Validate unique surface IDs, unique operation IDs within a surface, valid type
  references, valid operation input references, and valid projection references.
- Entity candidates remain surface-scoped.
- REST execution attachments are present but separated from normalized
  projection-facing fields.

### 5. OpenAPI Importer

- Imports GitHub-shaped OpenAPI fixtures without network access in unit tests.
- Uses the documented first-wave OpenAPI 3.0.x subset and Coral-owned serde
  model.
- Handles path/query/header/cookie parameters needed by the acceptance slice.
- Handles singleton, list, and wrapped-list responses.
- Detects pagination for the acceptance slice.
- Assigns deterministic operation IDs.
- Emits diagnostics for skipped unsupported operations.
- Refuses unpinned remote source documents.

### 6. Projection Generation

- Generates projections without author-provided projection entries.
- Produces stable names, columns, inputs, and visibility using the documented
  identifier, collision, column-flattening, and projection-kind rules.
- Skips unsupported or mutating operations by default.
- Generates usable projections for GitHub issue list, search, and get.
- Produces diagnostics explaining skipped operations.

### 7. Surface Input Binding

- Source add computes the union of all surface input declarations.
- Compatible repeated input declarations are prompted once and persisted through
  the existing source-scoped source state.
- Conflicting repeated input declarations fail validation with errors naming the
  source, surfaces, and input key.
- Compatibility uses exact structural equality over `kind`, `required`,
  variable defaults, hints, and secret credential method definitions.
- Runtime lookup resolves variables and secrets for the surface executing the
  projection.

### 8. Materialization

- Bundled/core sources do not embed OpenAPI documents or pre-built IR in the
  Coral binary.
- Source add fetches/reads pinned descriptions, verifies hashes, imports IR,
  generates projections, validates artifacts, and writes materialized state.
- Existing source add rollback behavior also removes partial materialized v4
  artifacts.
- `fingerprint.yaml`, `diagnostics.yaml`, `projections.yaml`, per-surface
  `semantic-ir.yaml`, exact `source-document.raw`, and normalized
  `source-document.yaml` are written.
- Query-time source loading performs no OpenAPI network I/O and no importer or
  projection generator execution.
- Missing/stale materialization errors point to source refresh or reinstall.

### 9. Refresh

- `coral source refresh <source>` exists.
- Refresh re-fetches pinned descriptions and verifies manifest hashes.
- Refresh writes into a temporary directory and atomically replaces artifacts
  only after full validation.
- Refresh uses unary `RefreshSource` API semantics and returns the refreshed
  source plus materialization diagnostics.
- Refresh does not run source `test_queries` or provider data endpoints.
- Hash mismatch reports the observed hash and leaves existing artifacts intact.
- CLI/MCP/API docs are updated for the new command surface.

### 10. Runtime

- V4 runtime registers DataFusion tables/functions from materialized projection
  catalog entries.
- The OpenAPI/REST physical planner executes generated GitHub issue projections.
- `QuerySource` carries an optional `V4MaterializedSource` payload and v4 engine
  compilation fails if that payload is absent for a v4 manifest.
- Multiple OpenAPI surfaces in one v4 source execute by dispatching projection
  entries through their `surface_id`.
- Runtime errors reference source schema, projection name, surface ID, operation
  ID, and missing input where applicable.
- Existing v3 runtime behavior remains unchanged.

### 11. End-to-End

- GitHub issue list/search/get queries pass through v4 after source add.
- Tests prove query-time execution does not fetch OpenAPI or run importers.
- Tests cover required filters/args, optional params, row conversion,
  pagination, singleton/list/wrapped-list responses, and surface-level input
  binding.

### 12. Docs

- Document v4 manifest shape.
- Document surface pinning and Coral-owned artifact mirror policy.
- Document automatic projection generation and the absence of manifest-level
  projection overrides in this wave.
- Document materialized artifacts and refresh.
- Document that v4 is OpenAPI-first and GraphQL is a fast-follow.
- Update docs in the same change as CLI/API/MCP surface changes.

## Resolved Design Decisions

- The v4 manifest variant is `ValidatedManifestKind::V4(Box<V4SourceManifest>)`.
- Missing OpenAPI `operationId` values use `<method>_<normalized_path>`.
- Generated SQL names and columns use the documented lowercase snake_case ASCII
  normalization and stable collision suffix rules.
- Table-vs-table-function selection uses the documented projection-kind rules.
- Importer and generator diagnostics are materialized in `diagnostics.yaml` and
  surfaced as summaries during source add and refresh.
- Both exact raw upstream OpenAPI bytes and a normalized parsed copy are persisted
  beside semantic IR.
- Multiple OpenAPI surfaces in one v4 manifest must materialize and execute in
  the first wave.
- Relationship inference is limited to surface-scoped evidence and hints. It has
  no runtime behavior before GraphQL support.
- Read-only projections over non-GET operations are skipped in this wave, even
  when a provider uses POST for semantically safe search.
